# Release guidelines: macOS and Windows

Releases are moving to GitHub Actions ([Releasing](RELEASING.md)); until that takes over, this file is the **operational source of truth for both platforms**. At the start of every scheduled or manual release, first synchronize local `main` with `origin/main` as below, then read this file from that synchronized commit. If a command, artifact, platform capability, or live endpoint differs from this guide, stop and reconcile the guide and implementation before publishing. Both platforms ship the same [Electron host](../platform/electron/README.md), packaged by `scripts/package-electron.ts`. Platform-specific implementation details remain in [Mac distribution](../platform/electron/DISTRIBUTION.md), [Windows distribution](../platform/electron/DISTRIBUTION.md#windows), and [Development](../scripts/DEVELOPMENT.md).

Scheduling and machine ownership are defined in Machine automation: each designated release host starts its own release slot three times a day (00:00, 08:00 and 16:00 America/Los_Angeles) with the model-free script worker, at its first free one-minute daemon tick in the slot; no Issue is opened (owner decision 2026-10-02). Do not run duplicate direct-release timers.

## Functional verification scope

Prioritize current product behavior and implementation over obsolete test assumptions. PR merge checks stay light (the required Architecture check: static/type/architecture checks and a load smoke of the automation code; the operational checks run in the RC, #1188, as described in [Development](../scripts/DEVELOPMENT.md)). Releases are comprehensive, and **ship only verified commits** (owner decision, 2026-09-30): the release worker builds the newest `main` commit after the last release whose full gate list — the commands in `scripts/gate.mjs`, the same for nightly gates and release-candidate runs — passed on that platform's release host (every OS gates `test:electron`; the Mac adds its Harness, Hermes and onboarding checks), recorded as the GitHub commit status `worldlet/rc-mac` or `worldlet/rc-windows`. It does not rerun that gate; it then verifies build/startup, distribution integrity and updates. If no newer commit passed, the slot is skipped and recorded in the release-check Issue; an unverified commit is never shipped. See release selection for the exact rule and the checks that remain at release time. Update or remove stale assertions in a reviewed PR instead of changing working behavior to satisfy them. A real functional failure still needs a fix. Keep required GitHub checks, package integrity, applicable signing/notarization and update/data-preservation checks. Record exactly what was checked; code review alone is not device acceptance.

Between releases, the release hosts run the same gate list on new `main` commits as model-free release-candidate runs. They run at most every two hours, outside the nightly window, and not in the 45 minutes before a release slot. One more RC may start 07:00–07:15, after the night's fix window, so night fixes can ship at 08:00. A failure is fixed by a repair PR from the release host, without an Issue, so the fix starts before the release; only after three failed attempts does the owner get an Issue (RC repair PRs). An RC run never uploads or publishes anything; its passing result, checks and package (#1102), is what makes a commit releasable. Each RC does take its platform's next Build and tags the commit `rc/<platform>/vYYYY.MMDD.BUILD` (#1091); the release that ships it reuses that Build and version.

PR CI runs every check (`check:pr`: the complete `check` plus `check:source`, `check:contracts`, `check:docs` and `check:style`, then the fast browser-free and operational checks) and no product test suite; both platform gate lists run the same checks and every test. History/durability/runtime/parity behavior checks and document/artwork validation remain release requirements.

Both platform gate lists include `test:ci`: the complete operational and focused trust group, even when an unrelated PR did not select it. Missing diff evidence in PR CI runs that group too. This selection never changes task capacity, claims, recovery ownership or live telemetry.

Windows packaging (Electron package plus NSIS installer) runs distribution, installation, updater, restore/data-preservation and startup smoke checks. The verified commit has passed the Windows gate (`npm run test:electron` and the shared suites) on the Windows release host before packaging.

All machines read this policy from synchronized main before taking a task. Development agents use focused checks; model-free release workers follow the checked scripts and never reinterpret or bypass a failed check at runtime.

## Rules shared by both platforms

1. **Synchronize before choosing a release commit, then choose a verified one.** Keep the primary checkout on `main`; confirm it is clean, unlocked and not being changed by another process. Fetch `origin/main`. If local `main` is behind, fast-forward it; if it is ahead or diverged, preserve local work on a feature branch and submit a PR before selecting a release. Never push main directly. Fetch once more and require local `main` and `origin/main` to resolve to the same SHA. Preserve every commit. If this cannot be done safely, stop and report the blocker. Never release an uncommitted or unsynchronized tree. From synchronized `main`, choose the newest commit after the platform's published source whose full gate passed on that platform; never an older, unverified or newer-than-main commit.
2. Compare **actual product commits** since that platform's latest published source commit. A release-identity commit, archive record, Windows-only change, or documentation-only change does not by itself trigger a Mac release; apply the equivalent rule to Windows. Shared `ui/`, `core/`, `contracts/`, `resources/`, `harness/`, `models/` and `platform/electron/` changes may affect both platforms. Review the diff, rather than treating every new SHA as a reason to publish.
   **Windows includes shared Core changes.** Any change since the last publicly released Windows source SHA that affects Windows functionality triggers validation and a new Windows release, whether it is in `core/`, another shared directory, `platform/electron/` or elsewhere. Judge actual functional impact, not directory names; the absence of Windows-specific code changes is not a reason to skip a release. For a no-release decision, record the published baseline SHA, synchronized candidate SHA and shared-directory diff evidence; documentation, tests, release metadata and content already included in the public package do not by themselves require repackaging.
3. **Isolate after synchronization.** Pin the chosen verified source SHA (at or before synchronized `main`) before building, then create a separate release worktree at that SHA with its own outputs. Do not build from the live main checkout. A newer `main` must not change that release's bytes. Changes arriving during the build stay on `main` for the next release; do not silently add them to a running build. Only one release per platform may run at a time.
4. [`release.json`](../release.json) holds a numeric native version (`YYYY.MDD.BUILD`) and **independent** `platformBuilds.mac` and `platformBuilds.windows` counters. Each Build belongs to one platform's counter. Since #1091 every release-candidate run takes the next Build of its platform (tag `rc/<platform>/vYYYY.MMDD.BUILD`), and the release that ships it reuses that Build and the RC's day, so public Builds skip the numbers of RCs that never shipped. Mac's legacy `build` field remains the Mac counter. The official release label is **`vYYYY.MMDD.BUILD`**, for example `v2026.0928.1076`. npm/native metadata omits the `v` and leading zero (`2026.928.1076`); `buildInfo` substitutes the selected platform's independent Build. Releasing twice on one day still gives two different Builds. New Mac GitHub tags use the official label; Windows tags use `windows-` plus that label to avoid cross-platform collisions. The release tag points at the source commit that passed the RC, on `main` beside its `rc/<platform>/v…` tag (#1129, 2026-10-01); the exact identity commit that was built (source plus the version files) is recorded in `release-identity.json`. Since 2026-10-04 (owner: "统一用git tag") the tag is the only release record: no identity PR is opened and `release.json` on `main` is no longer advanced by releases. Earlier release tags point at their identity commit. Historical tags stay unchanged. Download filenames retain the native-version-plus-build transport shape because existing Windows updaters validate that exact path; the version inside that filename is the new numeric identity. Never reuse an already published version/Build for different bytes or move an update feed backward.
5. Check the exact package and live download/update route after publication. Preserve previous installers and update entries subject to the retention policy below. Never commit credentials, personal data, OAuth tokens, or signing keys. Report a failed or partial release; do not label a reserved version commit as published.
6. Do not deploy the marketing website as a side effect of releasing a desktop app. Update website copy or the distribution dashboard only when the relevant channel status actually changes and through its own reviewed deployment path.

## macOS: scheduled production release

**Release notes:** Before preflight, compare the pinned source with the previous published Mac source and write concise English, user-facing Markdown notes to an absolute file outside the release checkout. Export `WORLDLET_RELEASE_NOTES_FILE` for both preflight and publication. Describe shipped improvements and fixes; exclude Windows-only changes, unreleased work, private information and internal implementation jargon. The preflight requires a nonempty file and the archive attaches it to the exact GitHub Release. It also checks the bucket-scoped R2 S3 credentials documented in [Mac distribution](../platform/electron/DISTRIBUTION.md#universal-dmg-s3-credentials), for a single streamed PutObject upload. Wrangler’s 300 MiB API limit is not a product size limit; R2 S3 supports single uploads up to 5 GiB. The fixed release worker prepares deterministic feature-area notes from the actual product diff; an operator may provide more specific notes for manual releases; a generic download/source stub is insufficient. Keep the notes with the exact GitHub Release and link verification in its release Issue; do not create per-build documents in `docs/`. A notes-only update does not trigger another installer release.

**Status and schedule:** Public Developer ID distribution. `elons-mac-mini.lan` runs the Mac release slot three times a day. It publishes only new Mac-relevant product work and never starts a second release while one is running. The interactive development Mac does not perform scheduled Mac publication.

**Source and build:** Only after local `main` and `origin/main` match, choose the newest Mac-verified commit up to `main`, compare its Mac-relevant commits and freeze that exact source SHA. Run `npm run release:local -- --commit <source-sha> --check`. If it passes, run `npm run release:local -- --commit <same-source-sha>`. The script creates the release worktree from the fixed SHA, builds the universal app with `package-electron.ts --arch universal --sign`, then runs the unchanged notarization, DMG and Sparkle appcast flow in `platform/electron/distribution/mac/`; use it instead of manually reproducing only some of its steps or bypassing a failed gate. Feature worktrees own behavior tests. The release gate runs the proportionate checks in the script, then validates the signed distribution rather than the full product suite.

**Required result:** Exactly **one** universal arm64 + x86_64 `.dmg` for macOS 14+, with the app and DMG Developer ID signed, Apple notarized and stapled. The final DMG has an immutable checksum and valid Sparkle signature. The package includes the intended Google Desktop OAuth registration but no user's grant. Upload the DMG and checksum to the existing release bucket (S3 PutObject with complete remote SHA-256 verification), update **both** `appcast.xml` and `appcast-intel.xml`, validate both live feeds and the download, then archive the exact build in a private GitHub Release. The script performs these steps and must finish successfully before reporting publication. Installed native-host apps reach the Electron app through these same feeds ([update path](../platform/electron/DISTRIBUTION.md#update-path-from-the-native-app)); verify that path for the first Electron release.

**Recovery:** An interrupted build may have pushed a release-identity commit without publishing an installer. Determine the live feed's Build and the candidate's exact source/bytes before retrying; do not publish a second copy merely because the identity commit exists. A partially uploaded installer is not complete until both feeds, download and archive are verified. Nothing is retained or resumed ([#991](../platform/electron/DISTRIBUTION.md#no-retained-candidates-or-resume-991)): a failed attempt ends, and the next scheduled slot builds again from its selected verified source. The exception is the RC package (#1102): an RC builds, notarizes and smokes its package, and the release publishes those bytes without building. After success the release tag marks the release; nothing is merged into `main`.

## Windows: separate preview release

**Microsoft Store:** Worldlet is live as Store ID `9P608B0R3F0Z` (publisher
`RenKelvin`), package `2026.1054.0.0` verified public on 2026-09-29 (#523). The
website's primary Windows link is the Store listing. The direct EXE below stays
available as a secondary installer with its updater, URLs and manifest unchanged.
Store submission is a manual Partner Center step. Record the Store package
separately from the EXE Build, and count it as published only once it is live.
See [Microsoft Store delivery](../platform/electron/DISTRIBUTION.md#microsoft-store-and-steam)
for channels, the release flow and the automation still missing.

**Status and schedule:** The live direct download remains the unsigned x64 preview (Build 1068 per the manifest checked on 2026-09-29), built by the former native Windows host; no Electron Windows build has been published yet. The Windows release host runs the Windows release slot three times a day through its model-free daemon and fixed release worker (no Issue since 2026-10-02); the old independent offset timer is superseded. On 2026-09-26 the publisher explicitly authorized **unsigned website preview releases starting with the next release check**, without waiting for signing or Store certification. This policy update does not itself trigger a release. Publish only new, validated Windows-relevant product work; retain truthful unsigned labeling and `signed: false`, and disclose possible Windows installation warnings. Continue the existing Store certification independently without cancelling or duplicating it. Windows 10 1809+ is the target; native-host Windows 11 x64 fixture evidence does not carry over to Electron, and Electron device acceptance on Windows 10 and 11 remains open.

**Signing gate:** Azure Artifact Signing account `clockless-worldlet` exists for Clockless Inc. Organization verification was submitted; the latest observed state and required publisher action belong in the [Windows release handoff](../platform/electron/DISTRIBUTION.md#windows-release-handoff). Do not resubmit unchanged information or assume certificate availability. After organization and certificate-profile readiness, integrate signing and timestamp verification for the application, uninstaller and installer. Verify the final packaged signatures and publisher, not just the manifest flag.

**Source and build:** Synchronize local and remote main, pin the exact source and use an isolated checkout. Run focused TypeScript, Electron distribution, installer integrity, upgrade and data-preservation checks. The release reuses the selected RC's Build (#1091); without one it reserves the next Windows Build when preparing an eligible release. Commit the identity before packaging. `npm run installer:windows` packages the Electron app and builds the unsigned NSIS [installer](../platform/electron/DISTRIBUTION.md#windows-installer); it is not yet the signed publication path. Build 1054 was reserved but not published after a native audio smoke failure; retain that evidence and do not mistake it for a public release.

**Update migration:** Build 1053's installed updater and the current download route/[manifest](../platform/electron/DISTRIBUTION.md#windows-preview-update-manifest) consumers accept only unsigned artifacts; the Electron updater keeps that manifest and verifies size and SHA-256. Installed native previews must update to the first Electron build through it, and native Windows libraries are not migrated automatically. Implement and verify a migration that preserves legacy clients before publishing a signed update. Do not simply change `signed` to true or overwrite an existing installer. Document the final route and manifest contract here when implementation and verification are complete.

**Required publication order:** For the authorized unsigned preview, validate exact source identity, unsigned labeling, size and SHA-256. Signed releases additionally require the signed workflow and update migration to pass, with publisher signatures and timestamps verified. Upload the immutable EXE and checksum to the existing release bucket, verify a complete public download, then publish the Windows manifest last. Validate the website download, actual updater discovery/download/hash checks (and signature checks for signed releases) and installer upgrade/data preservation. Keep the previous manifest if any gate is unavailable; never change Mac feeds. Record code, fixture acceptance and actual public publication separately in [Windows distribution](../platform/electron/DISTRIBUTION.md#windows) and update the [distribution dashboard](../platform/distribution/index.html) only when channel status changes.

**Notification boundary:** Stay quiet when signing status is unchanged or no relevant product changes exist. Notify only for a release, important fix, failure or a newly required publisher action. This Windows heartbeat does not establish a Mac release, real-account acceptance or clean-machine acceptance.

## Scheduler decision checklist

| Question | Action |
| --- | --- |
| Local `main` and `origin/main` cannot be safely made identical? | Stop before creating the release worktree; report the specific blocker. |
| No product commit relevant to this platform since its published source? | Stay quiet. |
| No commit newer than the published source passed the full gate on this platform? | Skip the slot: record it in the run (`State: no-release`, with each newer commit's result); never ship an unverified commit. |
| Newest verified commit has Mac-relevant changes and the Mac host is available? | Pin that verified SHA; preflight; run the isolated Mac release; verify public artifacts; sync `main` again. |
| New Windows-relevant commit on a Mac host? | Leave it for the separate Windows workflow; do not increment Mac Build solely for it. |
| Build/version reserved, but no validated public installer and update source? | Report partial/failed; do not call it released or create a duplicate release. |

## Release artifact retention

After a verified publication, under the same platform release lock, run:

```sh
node scripts/release-retention.mjs mac --dry-run
node scripts/release-retention.mjs mac --apply
# Windows owner uses windows instead of mac.
```

Use reviewed main tools and bucket-scoped R2 S3 credentials. Keep all artifacts
from the last 30 days, at least the three highest successful Build numbers per
platform, and the latest installer referenced by each current update feed/manifest.
An installer and its checksum expire together only when both object timestamps
are older than 30 days. Migration or re-upload therefore extends retention safely.
Mac success evidence is published appcast history; Windows uses published GitHub
release assets and its current manifest. Unarchived/unknown/incomplete files are
preserved. GitHub archives are not deleted by this policy.

Mac cleanup removes expired historical appcast entries with conditional writes
before deleting their files; it never removes either feed's newest target. Only
the platform owner runs its cleanup, with no concurrent publisher for that platform.
A changed feed/object aborts cleanup. Missing credentials or failed cleanup must
be reported separately; they never invalidate or roll back a successful release.
Do not configure blanket R2 lifecycle expiration: it cannot preserve the minimum
versions and active update targets.
