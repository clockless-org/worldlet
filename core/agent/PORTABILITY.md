# Portable Agent architecture

Worldlet gives your Agent a world to live and work in. The official distribution defaults to Hermes; custom adapters must implement the same world-facing contract.

The host side lives in the Electron host's `platform/electron/src/modules/agent-runtime/`: adapter selection in `index.ts`, Hermes in `hermes.ts` and `hermes-worker.ts`, executable adapters in `external.ts`, companion files in `hermes-files.ts`. The type and class names below (`AgentAdapter`, `HermesSourceAccess`, `AgentRoutines` and so on) carried over from the retired native hosts. Native-host acceptance recorded below ended with #996 and does not carry over: Electron device acceptance is still pending, and checks that existed only as Swift fixtures or native `--*-check` flags are named as not yet ported.

## Protocol v1

### One foreground Fox conversation

Fox uses one main conversation per companion identity/session generation and privacy scope, across Applets and content. The host does not hash the view key into the session (`platform/electron/src/modules/fox/companion.ts`). Hermes and external adapters receive the same host-owned session identity. Private, setup and practice remain isolated; background source checks and Applet work are not merged into Fox's conversation or relabeled as Fox. The UI shows one visible thread per context over this one session ([conversation](../../ui/companion/CONVERSATION.md#one-session-one-visible-thread-per-context)); that split is presentation only and never reaches the adapter.

The current view is replaceable environment reference data, attached at turn start. Idle navigation updates the UI snapshot immediately without a model call; executable protocol v1 delivers that environment on the next request. Navigation no longer aborts an ordinary foreground turn. Completed off-screen replies enter shared history but stay attributed to their original view; another content item's cached reply is never used as a fallback. Relative UI actions are rejected after the user changes views, while explicit record-ID operations can continue. Fox's steps on its own page held for its task also continue: the page in the task picture-in-picture window, or taken back from it into the panel during the turn (#1175). Queued messages whose original view changed stay in the input as drafts; supplements from a different view are not steered into the old task.

Stateless adapters receive a host-scoped `history` of up to six preceding visible messages. Session-owning adapters must not replay this fallback into an existing transcript. Full portable archives and old per-context Hermes sessions are retained, not concatenated or deleted. The main session starts fresh with archive recall available; the UI migrates its last saved view history as a bounded continuity seed without inventing an ordering across legacy view caches.

Checks: `companion-main-session-check.ts` covers shared history, latest environment, in-flight navigation, relative-action guards (and Fox's held page), off-screen reply attribution, persisted recall and queued draft safety. The native self-check for identical sessions across views, stable restart and privacy-scope isolation retired with #996 and is not yet ported to Electron. These are fixtures, not real-provider acceptance.

### Transport

Ordinary guides (including source-less connection receipts) expire on Area/Applet/content navigation, along with their suspended and dismissed copies. Closing onboarding connection UI explicitly clears its guide. Explicit priority approvals/model gates and locked first-use journeys retain their required decisions; navigation is never implicit approval.

Context presentation stays visible in an Area, Applet or open content without hover. It shows only an exact-view saved reply, otherwise a local contextual invitation naming the visible selection. Ambient copy does not run an Agent, claim to have read the source, or enter the main transcript. Overview retains its dismissible behavior; guides keep priority. Switching between contents of one Applet updates the invitation immediately, including while an earlier turn is still working.

`contracts/agent.ts` defines capability descriptors and chat events. The web bridge is `agentChat`, `agentCancel`, `agentSteer`; the host router still accepts the old Hermes request names (`hermesChat`, `hermesSteer`, `hermesCancel`) for compatibility. Reply callbacks are `worldletAgentEvent` and `worldletAgentTool`. Current UI contains no Hermes-specific streaming callbacks.

Events are `status`, `progress`, `response_start`, `delta`, `steered`, and `tool`. Tool requests carry an ID, name and object arguments, and await an execution receipt. Host configuration and Applet status events are validated by the host and are not rendered as chat. Adapters normalize transport events before delivery; unknown/malformed events fail explicitly. Request IDs and runtime metadata are not conversation content.

`progress` optionally carries `activity`, a presentation-only foreground phase
from [the shared allowlist](../../contracts/companion-activity.ts). Existing adapters
can omit it: Worldlet maps exact World tool implementation IDs, including resolved
gateway dispatch, rather than guessing from localized status prose. Unknown tools
remain generic work. `status.stage: waiting` selects service waiting. Phases never
authorize an operation, prove success, or attribute Applet background work to Fox.
The host validates it with the shared Core event validator (`agentEvent`). Input/listening/reply states take precedence.
See [animation readiness](../../ui/companion/ANIMATION.md): a semantic phase is not proof that
its dedicated artwork is finished.

Cancellation belongs to the requesting turn. Tool execution stays in Worldlet's existing permission gateway: an adapter cannot grant private-context consent, authorize accounts or turn a greeting into permission to act. Conversation metadata must never place text or tokens in the world event ledger.

## Data ownership target

Worldlet owns portable companion identity, personality, long-term memory, user-visible conversation archives, source citations, items and layout. Adapters own transient execution sessions, compression state and caches. Credentials are separate and excluded from portable exports. Hermes remains the live memory writer while selected. World automatically persists supported durable memory checkpoints and lets replacement external adapters read them without Hermes; these are not two independently mutable memory stores. See [World storage](../items/STORAGE.md) for domain ownership, checkpoint timing and remaining adapter limitations.

Use one open-source repository and one official composition. Separate repositories are optional for third-party adapters or future hosted billing/model services, not required for a signed desktop build.

## Companion archive v1

### Built-in personality and user overrides

`core/companion/default-persona.json` is the single built-in personality definition:
warm, witty and on the person's side, a friend who speaks up when it helps. Whatever
the personality, `core/companion/fox-voice.ts` adds how Fox talks (a friend texting,
not a help desk: no filler, length matched to the person, emoji only after theirs;
owner request 2026-10-06). Shared Core resolves a blank/whitespace
archive personality to this default; nonempty saved personality replaces it. The
archive retains the override, not a copied default, so upgrades also reach older
empty profiles without rewriting UUIDs, creation dates, memories or conversations.
Clearing the override restores inheritance. The Profile panel and speaking-style
guide use the same resolver for their default description.

The host builds archive prompts through Core `companionPrompt`, so every OS uses this shared policy.
The same resolved context is passed to Hermes and external adapters. Hermes no
longer labels the entire context as user-authored prose. The context explicitly
gives Worldlet personality priority over conflicting legacy Harness/SOUL tone,
without changing permissions or memory ownership. SOUL files, live memory writers,
credentials and attached external profiles are not rewritten, except that a `SOUL.md`
Hermes seeded itself in Worldlet's own Hermes becomes the companion's default persona
([default persona](../../harness/hermes/README.md)). This is prompt-level
precedence, not a guarantee about how every third-party model follows instructions.
Existing nonempty/imported preferences remain overrides, including legacy text;
they are never guessed to be disposable defaults.

Host session/storage behavior is unchanged; one Electron implementation assembles
memory on every OS. Model behavior and device acceptance on each OS require
separate verification.

Focused checks: `shared-companion-core-check.ts` covers inheritance, reset, all
memory authorities and non-mutating resolution, and the host calls the same Core
in-process (`platform/electron/src/core.ts`); `companion-persona-ui-check.ts` covers
the profile display; `companion-persona-harness-check.py` exercises the real Hermes
adapter against a loopback model with temporary profiles and unchanged SOUL files.

The companion profile (the portable `worldlet.companion` archive; the World keeps it in `world.sqlite` `companion_profile`, before 2026-10-03 `companion/profile.json`) has a format identifier, version, stable identity UUID, name, creation timestamp, personality, explicit memory authority, typed memory records and user-visible conversation turns (kept in `companion_turns` and added on export). Only Worldlet-owned records go here; provider tokens, tool execution state and credentials are excluded. Existing app name/style preferences seed a new archive once. Subsequent Agent turns use the saved identity/personality, and explicit name/style changes update the archive.

Private, setup and practice profiles are kept apart (scopes `private`, `setup`, `sample`; their conversations use separate databases under `companion-profiles/`). Both are excluded from private chat context. Active conversation segments roll over after 500 entries into owner-readable history files rather than dropping old conversations. Standard backup includes private/setup archive files and history; practice stays separate.

Hermes remains the declared memory authority until explicit handoff. Merely exporting a memory snapshot must not start injecting a second copy into every turn. Explicit imports into an external adapter switch authority to `worldlet`; imports into app-owned Hermes transfer the memory files and retain `hermes` authority. Export leaves existing SOUL and Hermes sessions untouched; a confirmed import replaces the app-owned memory/SOUL files. Birthday is not inferred from the profile creation timestamp.

Validation: shared Core validates every archive (`companionValidate`), and `shared-companion-core-check.ts` covers prompt bounds and recall. The native archive/transfer/recall fixtures (stable identity, style, typed memory, history, round-trip, unsupported version, duplicate IDs, unknown memory authority, isolation and mode 0600) were Swift-only and are not yet ported to Electron. None of this proves a live model migration.

Hermes Agent, OpenClaw and pi are the person's own Agents, and Fox talks through them directly (owner decision 2026-10-07: Worldlet builds the World, not another Agent): choosing one saves it in `agent/local-harness.json`, each foreground turn runs on that Agent's own sign-in, model and memory with World tools ([below](#world-tools-through-mcp)), and the World's background model work runs on that Agent too ([background work](#background-work-while-fox-talks-through-a-local-agent)). At launch a saved Harness that is no longer installed leaves Fox without an Agent ([no Agent](#no-agent)); `WORLDLET_AGENT_CONFIG` still takes precedence over both. Turns run in a Worldlet-scoped working folder with the person's own environment (so the Harness keeps its sign-in) minus `WORLDLET_*`. Claude Code's command line does not depend on the prompt (`LOCAL_HARNESS_SPARE`), so when a foreground turn ends the host starts the next turn's process right away (`SpareTurns` in `agent-runtime/local-harness.ts`), with its World tool bridge, and it waits with its sign-in, settings and MCP server loaded; the next turn with the same command line (same working folder, instructions, tools and world) writes its prompt to it, and any other starts its own (owner request 2026-10-06: Fox on a local Agent was slow). A spare is stopped after 10 minutes unused, on shutdown and when the Harness changes; each bridge has its own token file, so a turn and a spare can share the folder. Measured in a cloud container with a real Claude Code 2.1: about 4.6 s to the first word and 5.9 s for a one-word answer cold, 3.0 s and 4.1 s with a spare. A turn of its own process carries Worldlet's companion personality, the last six visible messages and the current view as reference data; a resident session carries only the new line and the current view, since the Harness keeps the thread. Worldlet keeps memory authority (`worldlet`).

### Resident sessions and approvals

Owner parity plan items 3 and 4 (2026-10-08): a process per turn was slow and carried only the last six messages, and Hermes Agent's own permission prompts were declined. The `conversation` service ([Harness services v2](../../contracts/HARNESS.md#harness-services-v2)) is now a resident session per Fox thread for the Harnesses that have one, and `approvals` brings their prompts into the World. Shared Core (`core/agent/harness-sessions.ts`) owns which thread a turn belongs to, the session names, the ACP permission mapping, the `/v1/responses` request and stream, and the Gateway WebSocket's connect frame, device proof and exec approval mapping; the host (`agent-runtime/harness-sessions.ts`, `AcpConversation`, `GatewayConversation` and `GatewayApprovals`) runs them; `LocalHarnessRuntime` uses one for the conversation's own turns (not setup's probe or background work) and asks no Harness by name.

- **Fox threads.** The chat's place thread decides the session (`harnessSessionThread`): an item card (`attention:<id>`) and an Applet (`object:app-<key>`) each have their own, everything else is the main conversation; the practice world has separate ones. The session name (`harnessSessionName`, `worldlet-<world>-<thread>-<hash>`) is stable across launches. Each session opened is remembered as Fox's own (`ownSession`, ledger `rememberOwnHarnessSession`), so the [history sync](#history-read-continuously) does not bring Fox's turns back as another conversation.
- **Hermes Agent.** One `hermes acp` process for every thread, started on the first turn on the person's own Hermes home and kept while the app is open (owner 2026-10-08: Hermes stays online), stopped on shutdown and when the Agent changes. `session/new` once per thread with Worldlet's MCP server for that session (a bridge that lives with the session; a greeting's turn refuses its tools), then `session/prompt` per turn; the instructions lead the session's first message and are sent again only when they change. Cancel sends `session/cancel` and ends the turn at once. Worldlet keeps the thread-to-session map in its own folder (`<agent home>/harness-sessions.json`); after a restart the thread's session is reloaded with `session/load` when Hermes offers it (`agentCapabilities.loadSession`; it keeps ACP sessions in its `state.db`), and its replayed history is not shown. A `session/request_permission` becomes an `{type:'approval',request}` turn event (`acpApprovalRequest`: the tool call's title and command, the choices its options offer, Deny always), shown as a card in Fox's dialogue (`ui/companion/fox-harness-approval.ts`: Allow once, Always, Deny) and sent to the paired phone with the live turn and as a notification; the answer goes through `harnessApproval` to `HarnessApprovals.answer`, which replies with the matching option (`allow_once`; for Always the `allow_always` option that outlasts the session, never Hermes' session-only `allow_session`, and Always is offered only when there is one; a reject option, else `cancelled`). The turn's idle deadline waits while the person decides; an unanswered prompt is declined after 10 minutes, and cancelling the turn declines it.
- **Hermes Agent's API server** (owner decision 2026-10-08: one path to whichever Hermes Agent Fox uses, [kept running](#hermes-agent-kept-running)). The main profile's threads go first to its resident API server (`HermesServerConversation`, `FirstAvailable` in `agent-runtime/harness-sessions.ts`): `POST http://127.0.0.1:<port>/v1/responses` streamed, with the profile's `API_SERVER_KEY` as the bearer token, the thread's session name as `X-Hermes-Session-Key` (Hermes keeps the conversation under it, with its own memory and compaction), the instructions and the new line, no `model` (Hermes answers with its own) and no client function tools: the pinned Hermes Agent 0.21.3's server runs only its own tools (`/v1/capabilities` says `tool_execution: "server"`), so World tools reach it as [World tools on Hermes](#world-tools-on-hermes), the `worldlet` MCP server registered in the profile, and Hermes' calls on it come back to the running Fox turn (its tool events and trust, as on a turn's own server; [which calls are its own](#world-tools-on-hermes)). Calls Hermes reports as completed `function_call` items are its own and skipped. Port and key are read from the profile (`hermesServerSettings` in `core/agent/hermes-server.ts`: its `.env` `API_SERVER_KEY`/`API_SERVER_PORT`/`API_SERVER_HOST` over `config.yaml` `platforms.api_server.extra`, default 8642). It is used while `GET /v1/capabilities` answers with that key and the profile has Worldlet's `worldlet` entry (`hermesWorldToolsRegistered`); otherwise the thread stays on `hermes acp` below, and why is recorded once in diagnostics (`hermesServer`), not said in Fox's reply, since `hermes acp` still keeps the thread. Its `/v1/responses` carries no approval events (only `/v1/runs` does), so a command that needs approval is not run there, as `chat -q` declines it; mapping `/v1/runs` approvals to the card is not done. An Applet's chosen model is not sent on this route. Other profiles (`hermes -p <profile>`) keep `hermes acp`. Fox's own sessions there are kept out of the history sync by their key (`hermesConversationIncluded` skips a `session_key` starting `worldlet-`).
- **OpenClaw.** Turns go to the person's running Gateway (`POST http://127.0.0.1:<port>/v1/responses`, [OpenResponses API](https://docs.openclaw.ai/gateway/openresponses-http-api)) with `model: "openclaw"`, the instructions, the new line, `stream: true` and the thread's session name as `x-openclaw-session-key`, so OpenClaw keeps the thread and compacts it. World tools are client function tools (the same two gateway tools); a `function_call` runs through the same World gateway as the MCP server and the response continues with `previous_response_id` and `function_call_output` (at most 24 rounds). The port and secret are read, never written, from the person's `openclaw.json` (`gateway.port`, `gateway.auth.token` or `password`, a `${VAR}` reference) or `OPENCLAW_GATEWAY_PORT`/`OPENCLAW_GATEWAY_TOKEN`/`OPENCLAW_GATEWAY_PASSWORD`; default 18789. Its tools run under its own settings, as with `agent exec`.
- **OpenClaw exec approvals** (`approvals: native`). They travel only on the Gateway's WebSocket, so while a Fox turn runs on a Gateway session the host (`GatewayApprovals`) opens one socket to `ws://127.0.0.1:<port>` and closes it when no turn listens. Protocol 4 ([Gateway protocol](https://docs.openclaw.ai/gateway/protocol)): the Gateway sends `connect.challenge` `{nonce,ts}`; Worldlet answers `connect` as an operator client (`client.id`/`mode` `cli`, `caps: ["approvals"]`, scopes `operator.approvals` and `operator.read` only, the shared secret in both `auth.token` and `auth.password`) with a device identity: an Ed25519 key Worldlet keeps in its own folder (`<agent home>/openclaw-device.json`, never in OpenClaw's), the device id the SHA-256 of the raw public key, signing `v3|<device>|cli|cli|operator|<scopes>|<ts>|<secret>|<nonce>|<platform>|` (`openClawDeviceProof`). A device-less operator gets no scopes; a loopback device is paired silently by OpenClaw's default (`gateway.nodes.pairing.autoApproveLocal`). An `exec.approval.requested` whose `request.sessionKey` is the turn's session (as sent, or `agent:<id>:<key>`, without case) becomes the same approval card (`openClawApprovalRequest`: the command with its warning, the decisions `allowedDecisions` offers, Deny always, the Gateway's `expiresAtMs`); other conversations' requests are ignored. The answer goes back as `exec.approval.resolve` `{id, decision: "allow-once" | "allow-always" | "deny"}`; `exec.approval.resolved` (answered in OpenClaw itself, or expired) settles the card; a request still open when the turn ends is declined. The HTTP stream waits meanwhile and the turn's idle deadline holds. When the socket cannot sign in (Gateway not reachable, wrong secret, the device not approved), the turn still runs, Fox's working card says once why, and OpenClaw decides by its own `askFallback`. Confirmed from OpenClaw 2026.9.8's own sources (`@openclaw/gateway-protocol` schema, `@openclaw/gateway-client`, its MCP channel bridge): frames, handshake, protocol version, the `v3` proof, scope and method names, the event payload and decision values. Assumed: that the WebSocket is served at the port's root path, that `cli`/`cli` with a device is silently paired on loopback with `operator.approvals`, and that a `/v1/responses` turn's exec requests carry the header's session key in that form; not yet verified against a running Gateway.

### History, read continuously

Owner parity plan item 5 (2026-10-08): bringing copies an Agent's conversations once, but the person keeps talking to it afterwards (a Discord channel, a Telegram DM, a terminal session), and those turns have to reach the World too. Every Harness with a reader serves the `history` service ([Harness services v2](../../contracts/HARNESS.md#harness-services-v2)) in mode `files` (`agent-runtime/agent-history.ts`, `filesHistory`): `threads(since)` lists the conversations written to after a time, and `turns(thread, cursor, limit)` returns the turns after a cursor, oldest first. They are the readers bringing uses, unchanged, so the same rules, limits and read-only opening apply. A thread is one conversation under the key bringing gives it (OpenClaw `<agent>:<session key>`, Hermes Agent the chain's first session, with `<profile>:` for another profile, Claude Code and pi the session file, Codex the session ID); a turn's ID is its place in that conversation (`"0"`, `"1"`, …), and a cursor is the last ID taken. A Claude Code, pi or Codex thread is listed by its session file's name and time alone, with an empty title, and its file is read only when its turns are asked for (the turns then carry the title); a Codex session ID comes from the file's name, else its first line. When a thread was last written to: the session file's time for Claude Code, pi, Codex and older OpenClaw, the newest message for Hermes Agent, the newest transcript event for OpenClaw's SQLite store (the database file's time when its events carry none).

One Harness-neutral sync (`fox/history-sync.ts`) runs while Worldlet runs: shortly after the World opens, then every five minutes, and two seconds after a watched Agent writes to its history, never during Fox's own turn, and only in the person's own World. It asks for the service, never for a Harness by name (`harnessService` in `core/agent/harness-services.ts`), for the chosen Harness, the Agent brought at setup and every Agent whose conversations the World already keeps. Each check lists the threads written to since the last check (less a minute; the first check of an Agent reads its whole history, owner decision 2026-10-08: the Agent itself carries the conversation, and the World keeps a copy for Attention, the phone and showing it), newest thread first, and appends only the turns after each thread's cursor to `companion_turns` (`addCompanionTurns`, never a replace), with the IDs bringing gives them, so a turn already brought is not added twice. A new turn joins the conversation it was brought into (its session name), even when the conversation has been renamed since. Where it got to lives in `world.sqlite` `harness_history`: one row per thread (cursor, session) and one per Agent saying when it was last checked. The sync runs on Worldlet's main process, where every website page's input and frames pass too (owner report 2026-10-08: pages lagged while 3151 read a whole history at once, every five minutes until it was through), so a check reads one thread at a time and lets everything else run between threads and pages of turns, stops after 1.5 s of reading (but reads at least one thread, so a slow listing on a busy computer still moves on), and never reads again a thread read through since it last changed (its row's `checked_at`; 0 for a thread left part-way). Limits: a check adds at most 8 MB of text; one that stops at a limit carries on a minute later; an Agent's whole history in the World stays within the 96 MB any brought history has, each turn within 128 KB. Bringing an Agent again forgets its cursors, and the next check reads its recent threads again without adding anything twice. When turns were added, Ongoing reads the conversations again (proposals and Attention context) and the page is told (`worldlet:ongoing`), which reloads the kept things' latest lines and republishes the paired phone's Applet world.

**New messages as they arrive** (blueprint "New messages afterwards", 2026-10-08). The `history` service may also `watch` (contract `HarnessHistory.watch`); `filesHistory` does it with `fs.watch` on where each Agent writes: Claude Code's `projects`, pi's `sessions` and Codex's `sessions` and `archived_sessions` folders (recursive, `.jsonl` files), Hermes Agent's `state.db` in its home and each profile, OpenClaw's `agents` folder (each agent's `openclaw-agent.sqlite`, older `sessions.json` and transcripts). On macOS `fs.watch` starts reporting a moment after it is asked (its FSEvents stream starts on another thread), and a write before then is never reported, so the databases a channel message lands in (Hermes Agent's `state.db`, OpenClaw's `openclaw-agent.sqlite`, with their `-wal`) are also compared by size and time 0.5, 2 and 5 seconds after watching starts. After each check the sync watches every Agent it reads; a write marks that Agent, and once writes have settled for two seconds (ten at most while it keeps writing) only the marked Agents are checked (after a check already running; while Fox answers it waits five seconds and looks again). The check is the same one-thread-at-a-time, 1.5 s check, and since it lists only threads written to since the last check and skips threads read through since they changed, it reads only the conversation that changed. A folder that cannot be watched is left to the five-minute clock, which keeps running for every Agent.

**The ones that matter go to Attention.** A thread is `shared` when other people write in it too (an OpenClaw session key with `:group:`, `:channel:`, `:room:`, `:space:`, `:thread:` or `:topic:`; a Hermes Agent chain with a `group`, `supergroup`, `channel`, `thread`, `forum` or `room` chat), not the person's own chat with their Agent. A new message there from after the previous check (not the first read of an Agent's history) that asks something, names a date or deadline, or mentions someone (`channelMessageAsks`: a question mark, "can you", "please", "let me know", "by Friday", "due", "tomorrow", "@name", their Chinese forms; no model) becomes a `channel` event (`channelMessageEvent`, with the three lines before it) handed to the Ongoing module (`OngoingService.channelEvents`). It joins the outside events as an observation of the `conversations` provider ([external events](../ongoing/README.md#attention)) framed for the Center's ordinary synthesis: Worth Doing when it asks the person for a reply, a decision or something by a date, worth knowing when it only concerns them, nothing when it was for someone else or the Agent already answered. There is no model call per message: the synthesis that already reads the conversations decides, and an item that cites the message reaches the phone once (`externalEventMatters` now counts `channel`).

**Fox's own turns never come back as someone else's conversation.** Fox talks through the chosen Harness, so its turns can land in that Harness's history. They are left out three ways: by the Harness's own marks (Hermes Agent's `acp`, `worldlet`, `cron` and similar sessions and `worldlet-` IDs; OpenClaw's `cron`, `run` and other machinery keys; Codex sub-agent runs), by where they ran (a Claude Code, pi or Codex session whose working folder is inside Worldlet's `agent/` folder, where every Fox turn runs: today `codex exec` keeps one session per Fox turn there, and bringing leaves those out too; a session run in any library's Fox folder, `<library>/agent/<private|sample|setup>/<Agent>`, is left out as well, so the Dev app's or a release check's Fox on the same computer is not brought as the person's conversation, also after that library is gone), and by the sessions the World knows are its own: `world.sqlite` `harness_own_sessions` (source, Harness session ID, Fox thread), written with `rememberOwnHarnessSession` when a resident session is opened. A thread any of whose sessions (OpenClaw's key, windows and current session, every session of a Hermes Agent chain, a Claude Code or pi file's session IDs, a Codex session ID) is remembered there is never read. Fox's turns stay where they are, in `companion_turns` under source `fox`.

`node scripts/harness-history-check.ts` (in `npm test`) brings fixture OpenClaw, Hermes Agent, Claude Code and Codex folders, chooses pi without bringing it, then appends to each one's history (a compressed Hermes Agent conversation, a renamed Claude Code session, a new OpenClaw transcript event) and checks that the sync adds exactly the new turns with the IDs bringing gave, under the conversation they were brought as, that Fox's Codex turns and a remembered resident session stay out, that reading again adds nothing, that bringing again starts over without duplicates and that the fixture folders are unchanged; that listing a session file reads only its name and time; and that a long history comes in over several short checks with each thread read once; and, watching every Agent, that a new OpenClaw channel message is read within seconds with only that Agent read, the one that asks something handed to Attention with the lines before it and the one that does not left out.

### Replying in a channel

Blueprint "Discord / Telegram / WhatsApp channels" (2026-10-08): Fox can answer in the channel thread a brought conversation came from, sent by the person's own Agent, once the person approved the exact text. It is the `send` service of [Harness services v2](../../contracts/HARNESS.md#harness-services-v2) (`HarnessSend`: `route(thread)` says where a message in a `history` thread would go, or null; `send(thread, text)` sends it), mode `native`, through the Agent's own command line with its own channel sign-in (`platform/electron/src/modules/agent-runtime/harness-send.ts`, rules in `core/agent/harness-send.ts`):

| | OpenClaw | Hermes Agent |
| --- | --- | --- |
| Where it goes | The session entry's `deliveryContext` (`channel`, `to`, `accountId`, `threadId`), else its `lastChannel`, `lastTo`, `lastAccountId`, `lastThreadId`: the route OpenClaw itself reuses for later delivery. Discord, Google Chat, iMessage, Matrix, Mattermost, Microsoft Teams, Signal, Slack, Telegram, WhatsApp | The chain's newest `state.db` session with a `chat_id` (and `thread_id`), on Telegram, Discord, Slack, Signal, WhatsApp, Matrix, Mattermost, SMS, Feishu or WeChat |
| How it is sent | `openclaw message send --channel=… --target=… [--account=…] [--thread-id=…] --message=… --json` ([docs](https://docs.openclaw.ai/cli/message)), every value as `--name=value` | `hermes send --to=<platform>:<chat>[:<thread>] --file - --json`, the text on stdin; bot-token platforms need no running gateway |
| Not offered | Sessions it delivers nowhere (web chat, the dashboard, cron, hooks) | Command-line, ACP, webhook and cron sessions |

Claude Code, Codex and pi have no channels and declare no `send`; an Agent not installed on this computer has no route. The World asks for the service by the conversation's Agent (`AgentService.channelSend(source)`, any brought Agent, not only Fox's), never by name.

Fox offers a reply with the World tool `reply_in_channel` (`companion/reply`: the conversation's name as `read_companion_archive` or an Attention item shows it, and the complete text). The host (`modules/fox/channel-reply.ts`) finds the conversation, its Harness threads (`harness_history`) and a route; when the Agent declares no `send` or the thread has no route, the tool says so and nothing is shown. Otherwise the offer is a guide in Fox's card (`ui/companion/fox-channel-reply.ts`): "Reply in Discord · #team?", the exact text, and **Send**, **Edit** (the text becomes a field; Send then sends what it holds) and **Skip**. Only Send sends (`channelReply` `send` from the card; the tool can only `prepare`), once; the card then says "Sent to …". What is sent is text: at most 4,000 characters, and a `MEDIA:` path or `[[…]]` directive, which both Agents' send paths would turn into an attachment from this computer, is refused. An offer waits a day; nothing is sent from the practice world. The phone does not show these offers yet.

`node scripts/harness-send-check.ts` (in `test:core`) checks the declarations, the route and command rules for both Agents against fixture folders with a fake command (the folders unchanged), that an Agent with no send path is not offered it, the offer, an edited Send, Skip and a second Send refused, and the card's Send, Edit and Skip.

## External adapter composition

`AgentRuntimeProvider` selects the explicit `WORLDLET_AGENT_CONFIG` executable configuration or defaults to Hermes. `ExternalAgentRuntime` owns version/capability handshake, event validation, scoped directories, request bounds, timeout and cancellation. The example and setup instructions live in [harness/example](../../harness/example/README.md). Source-service backends and model configuration are optional adapter services; the example explicitly does not implement them. External mode skips automatic Hermes preparation, prewarm, world checks and Hermes routines. It can negotiate its own model-configuration and scheduled-execution capabilities. Unsupported connected-source requests fail explicitly.

Evidence: `npm run test:electron` (module `agent-runtime`) runs a real executable fixture through `external.ts`: handshake and minimal environment, a streamed turn with a World tool round trip, cancellation and bad-configuration fallback to an unavailable adapter. `external-agent-ui-check.ts` streams the real example process into the actual UI and opens Browser via Worldlet's existing tool execution path; its host bridge is a fixture. ## Legacy conversation conversion and import isolation

## Portable recall

`read_companion_archive` (gateway `companion/recall`) searches portable memories and archived visible conversations, and reads full records using character offsets. Search returns up to five bounded excerpts; record reads are paged at 3,000 characters. The prompt includes at most 8,000 memory characters and points to recall for the rest. World-owned Hermes checkpoints are available as reference data through host recall; their bounded prompt excerpts are supplied to replacement external adapters, while Hermes retains its own live injection. Host consent and personal-world checks apply to this tool just as to other private reads. The example executable's `recall companion` demonstration calls this real protocol tool; the retired Swift adapter fixture imported a Hermes-format memory, converted ownership, served the recall request and verified the returned text (not yet ported). `shared-companion-core-check.ts` verifies Unicode retrieval and prompt bounds in shared Core; the Swift paging and foreign-memory isolation fixture (`companion-recall-check.swift`) is not yet ported. ### Calling from an Applet

Kelvin 2026-10-08 (the blueprint's Phone calls row): a call can start from the Applet that needs it, with its context filled in, and the World follows it live. Through the same `calls` service, which gains three optional parts: `placing()` (whether the Harness can dial now, else a note saying how to set it up), `place({to,message})` and `hangUp(id)`, plus `live` on a call in progress. The World asks the Agent service, never a Harness name.

1. **The Applet offers Call** on an item with a phone number. Messages does today: a conversation with one person whose address is a number (`conversationCallBrief` in `core/ongoing/harness-calls.ts`; a group or an email address has none). Its data fills in the brief: whom (the Contacts name and the number, E.164 only, never a guessed country code, `callNumber`), why (the last thing they said) and what to find out (the person's own question when it is the conversation's last line and still unanswered).
2. **The person confirms it** in Fox's card (`ui/companion/fox-call.ts`): whom it calls and from which Applet, Why and What to find out to edit, the exact opening the Agent will say (`callOpening`: that it is an AI assistant, for whom, why, the ask), that a call cannot be taken back, and **Call** and **Cancel**. The host keeps the brief (`harnessCall` `prepare`, in `platform/electron/src/modules/ongoing/harness-calls.ts`) with the number and name from the Applet; only the card's Call dials (`place`, once), with the person's edits. Nothing is dialed from the practice world.
3. **The Agent dials** through its own calling. OpenClaw: the voice-call plugin's own command, `openclaw voicecall call --to <number> --message <opening> --mode conversation`, which goes through the running Gateway (`voicecall.initiate`) and prints `{"callId":…}`; a conversation call stays open after the opening and the plugin's voice agent answers the other party with the opening, and so the ask, in its transcript. Dialing is offered when `plugins.entries.voice-call` is enabled with a `provider` in `openclaw.json`; otherwise Fox says what is missing (`openclaw plugins install @openclaw/voice-call`, or `openclaw voicecall setup`). **Hang up** runs `openclaw voicecall end --call-id <id>`.
4. **The World follows it live.** Once a call is placed, and whenever any call is in progress (placed here, by Fox, or someone calling the Agent), the store is read every 1.5 seconds instead of every 30 (`HARNESS_CALLS_LIVE_MS`; the plugin writes a snapshot at every change, so no new service or watcher is needed). Each change reaches the page (`worldlet:harness-call`) and Fox's card shows the status line (`callStatus`: "Calling Anna…", "Ringing Anna…", "On the call with Anna · 1:05", the clock ticking), the transcript as it grows (the newest 40 lines) and Hang up; when it ends, how it went (`callLine`). A record still in progress after two hours is stale and not shown live. The ended call then becomes Attention context as above.

Hermes Agent has no call path the World can use: its optional `telephony` skill can place a call when asked in a chat, but it keeps no record and has no command Worldlet could run, so it keeps no `calls`. Pressing Call there, or with any Agent without dialing, has Fox say so plainly and how to get it (`harnessNoCallsNote`: OpenClaw with its Voice Call plugin as Fox's Agent). Compared with OpenClaw on its own, where a call starts from a chat or the CLI with whatever words the person types: here it starts from the item it is about with the context filled in and shown before dialing, and its status and transcript stream in the World while it runs.

`node scripts/harness-calls-check.ts` (in `test:core`) checks the brief, the opening, the status line, the plugin's command line and its answer, dialing and live reading against a fixture store and a fake command, the host's prepare, place, cancel and hang up, and the card; `scripts/messages-check.ts` (in `test:ui`) clicks Call in the Messages Applet with a mocked host. Not yet seen on a device: a real call placed this way (the command line's output is read from the plugin's source), and that `voicecall call` without a running Gateway, which falls back to a runtime inside the command, keeps the call going after the command ends; Worldlet assumes the Gateway runs.

### Scheduled routine capabilities — 26 September 2026

User-requested Hermes routines run only while the app is open/awake and permitted.
A routine whose time passed while the computer slept or Worldlet was closed runs once
when it wakes or starts, not once per missed slot, and the world log says it ran late
(Core `routinesDueAfterGap`; the host only reports the resume and never keeps the
computer awake). `node scripts/routine-catch-up-check.ts` (in `npm test`) covers the rule
and module `fox` in `test:electron` the resume wiring.
Their allowed tools are web research, Hermes memory/skills and the bounded Google
read adapter when authorized. Foreground MCP connections are not inherited:
a connected server may expose writes or external messages that have no unattended
confirmation surface. Existing saved jobs also receive the current restricted
toolsets at execution, rather than trusting their persisted tool list. Unsupported
script/delivery modes pause for review in Fox. Source-check jobs remain separate
from these user-authored routines.

`python3 scripts/routine-permissions-check.py` verifies that boundary with a mocked
scheduler, including restored toolsets, cancellation, Google read dispatch and
unsupported modes. It does not establish real cron scheduling or model execution;
`test:hermes:routines` is the separate pinned-Hermes execution fixture.

### User-managed saved memory

Fox's Memory → Manage opens About you and Long-term memory for explicit review. Saving requires a second confirmation and a matching archive revision. The app pauses its owned runtime, writes live memory and the portable checkpoint with rollback on failure, and starts a fresh foreground context. Attached/external agents are read-only. Each edited section is pinned in `companion/memory-edits.json`; subsequent checkpoints cannot overwrite it. The prompt includes the user-corrected section even when Hermes owns ordinary memory.

This is section-level management, not semantic fact deletion. Clearing a section does not erase conversations, sources, existing exports or all information the model might infer from them. Automatic memory still operates outside these pinned sections. Per-fact evidence/conflict handling remains incomplete, and editing has device acceptance only from the retired Mac host.
