# Agent identity, Grants and audit

Every Agent that reaches the World through the `worldlet` MCP server is its own identity, with its own list of Grants and its own audit trail. Anyone running Worldlet can see which Agent did what, give one Agent more or less than another, and revoke one without touching the rest.

The shapes are in [`contracts/agent-identity.ts`](../../contracts/agent-identity.ts); the decision is in [`grants.ts`](grants.ts); `node scripts/agent-grants-check.ts` checks both.

## Identity

An `AgentIdentity` has a stable ID (lowercase letters, digits and `-`; it names the Agent's endpoint file and its ledger rows), the name the person knows it by, its Harness (`hermes`, `openclaw`, `claude-code`, `codex`, `pi` or another adapter's ID), whether it runs on this computer (`local`) or another (`remote`), when it was created and last seen, and when it was revoked. A revoked Agent's calls are denied.

## Grants

A `Grant` gives one Agent a list of World gateway `target/action` patterns (`items/query`, `items/*`, `applet:*/launch`, `*/*`; `*` matches anything, including `/`) with:

- **access**: `read` covers reads only; `write` covers reads and writes. The host says whether a call writes (the turn rule's guarded writes and the gateway's write actions).
- **duration**: `standing` runs without asking until it is revoked or expires; `once` lets reads run and sends each write to the person's approval card (Allow once or Deny).
- optional `expiresAt` and `revokedAt`: a Grant past either counts for nothing.

`grantDecision` decides one call, in this order:

1. An unknown or revoked Agent is **denied**.
2. **The turn rule comes first** ([`turn-trust.ts`](turn-trust.ts)): a write the turn has refused, because untrusted content entered it, stays refused whatever the Grants say, with the turn rule's own words. A Grant never widens what a turn may do.
3. With no active Grant of this Agent matching the call, it is **denied**. A write matched only by `read` Grants is denied.
4. A matching `standing` Grant **allows**. Under a `once` Grant a read is **allowed** and a write is **asked**.

`describe_world_tools` lists only the targets one of the Agent's Grants names (`grantCoversTarget`).

## Audit

Each decision becomes one `AgentAuditEntry` (`at`, `agentId`, `target`, `action`, `decision`: `allowed`, `denied` or `asked`, the `grantId` that decided and a short `reason`), kept in the ledger as `agent.audit`. `keepAgentAudit` keeps the newest `AGENT_AUDIT_KEEP` entries per Agent, so a busy Agent never pushes out another's history.

## Who saved what

World items, artifacts and the Attention items built from them carry an optional `agentId`: the Agent that saved them. Hosts stamp it from the token that made the call (`prepareWorldItem` and `mergeArtifact` take it as an argument). A model never sets it: an `agentId` in what a model sends is dropped, and a saved record keeps the Agent that first saved it.

## The standing MCP server

The `worldlet` MCP server registered in an Agent's profile (World tools on Hermes, [PORTABILITY.md](PORTABILITY.md#world-tools-on-hermes)) is where Grants are enforced, on the Electron host and the [Node host](../../platform/node/README.md) alike (`agent-runtime/world-tool-bridge.ts`, `agent-runtime/agent-access.ts`):

- **Its own token and endpoint file.** Each run, each Agent gets a new token, written with the endpoint to `worldlet-mcp-endpoint.<agentId>.json` in its profile (owner-only, removed on quit). Only the token's SHA-256 hash is kept, in the vault (`agent-token:<agentId>`); a call is identified by its token, and an unknown token is answered as if Worldlet were closed. Identities and Grants are kept with Fox's setup choices (`agent_settings`, `agent-access`), so they follow the World and its backups.
- **Default Grants.** An Agent's default Grants are what a call outside any Fox turn could do before Grants existed (`HERMES_CHANNEL_TOOLS` in [`hermes-server.ts`](hermes-server.ts)): a standing `read` Grant for reads and a draft for the person's review, and a standing `write` Grant for `world/link`. They are written again each run so new Applet sources are covered (`channelDefaultGrants`). Worldlet Services (`read_service`: `github/list`, `github/read`, `github/search`, [INTEGRATIONS.md](../applets/INTEGRATIONS.md#github-service); `posthog/query`, `posthog/read`, [PostHog](../applets/INTEGRATIONS.md#posthog-service); `cloudflare/read`, [Cloudflare](../applets/INTEGRATIONS.md#cloudflare-service)) are never in the default Grants, since a Service can return other people's text or personal data: an Agent reads one only through a Grant the person gives it in [Settings › Agent › Access](#settings--agent--access) (`serviceReadGrant`), and a call its Grant admits outside a Fox turn runs its read as the default reads do.
- **Calls.** Outside any Fox turn, a call is a turn of its own that starts untrusted (except the browser link), so the turn rule refuses its writes first. Any refusal but a revoked or unknown Agent's says what such a call may do: `HERMES_CHANNEL_READ_ONLY` for Hermes Agent, `STANDING_OUTSIDE_TURN` (which names no Hermes channel) for another Agent such as Claude Code or Codex. `channelToolReply` (Fox's module) checks the same Grants again before it runs anything. While a Fox turn holds the server, Hermes Agent's calls go to the turn as before (Fox's turns run on Hermes Agent; another Agent's calls are always its own, under its own Grants) (`foxTurnGrant`): reads run, a write the turn's own stream announced runs, and any other write goes to the approval card, which names the Agent (`asked`) (`standingCallDecision`).
- **Discovery.** `describe_world_tools` lists only the targets the Agent's Grants name (`standingActions`).
- **Audit.** Every call's decision is appended to the ledger as `agent.audit`, keyed by the Agent, and only its newest `AGENT_AUDIT_KEEP` entries stay. Last use is stamped on the identity at most once a minute.
- **Revoke.** Revoking an Agent stamps `revokedAt` on it and its Grants, deletes its token hash and removes its endpoint files, so its registered server answers that Worldlet is not open. It stays revoked across runs.
- **Upgrading.** A Hermes Agent registered before per-Agent tokens names the profile's single `worldlet-mcp-endpoint.json`. On the first run after the upgrade, Hermes Agent becomes the `hermes` identity with the default Grants, and that file holds the same token for that run. Its registered entry is outdated, so `hermes mcp add` saves the new file's path and its gateway restarts. The old file goes on quit.

Agents in the cloud reach the same server's call through [remote MCP](REMOTE-MCP.md): each connection the person allows is an Agent of its own (kind `remote`), with the same default Grants and audit.

`node scripts/harness-sessions-check.ts` checks the token, the files, migration, default Grants, discovery, audit and revoke against a fixture Hermes Agent.

## Settings › Agent › Access

The Access part of Settings › Agent ([`ui/companion/agent-access.ts`](../../ui/companion/agent-access.ts), host action `agentAccess` in `agent-runtime/index.ts`) lists each Agent, the one used most recently first. For each it shows where it runs, its last use (or when it was revoked), its active Grants in plain words, and its five newest audit entries. Revoke asks once more in the page and then calls `agentAccess` `revoke`. That stamps `revokedAt`, deletes the Agent's token hash and removes its endpoint files. The page names places in the World and what was allowed. It never shows tokens, endpoints or MCP, except Remote access at its top, which shows the one address the person copies into a connector ([REMOTE-MCP.md](REMOTE-MCP.md)).

Under an Agent that is not revoked, each connected Worldlet Service has a **Can read <Service>** checkbox (Can read GitHub, PostHog, Cloudflare). Turning it on calls `agentAccess` `grantService` with the Agent and the Service's name; turning it off calls `ungrantService`.

Under them, **Can see your board** and **Can set up your board** give or take back the Agent's [board](#the-board) Grants the same way (`agentAccess` `grantBoard` and `ungrantBoard` with the Agent and `read` or `define`).

Once a GitHub App is connected (Settings › Agent › Connections, [GitHub drafts](#github-drafts)), **Can draft GitHub changes** gives or takes back the Agent's GitHub draft Grant the same way (`agentAccess` `grantGithubDrafts` and `ungrantGithubDrafts` with only the Agent).

Under them, **Can report its work** and **Can see other Agents** give or take back the Agent's [report](#agent-reports) Grants the same way (`agentAccess` `grantReports` and `ungrantReports` with the Agent and `report` or `list`). Above its Grants, the Agent's row says what it last reported and when ("Working: Building the installer · Fix the build · reported 3 min ago"), or "Quiet" or "Offline" once its report has run out.

Under it, **Can ask you** and **Can take work** give or take back the Agent's ask Grants the same way (`agentAccess` `grantAsks` and `ungrantAsks` with the Agent and `ask` or `work`; the page sends no targets; [Agent asks](#agent-asks)). The page shows each change as "You allowed it" or "You turned it off", and an answer as "You answered its ask".

**Can see your tracked links** and **Can keep your tracked links** give or take back the Agent's [tracked links](#tracked-links) Grants the same way (`agentAccess` `grantLinks` and `ungrantLinks` with the Agent and `read` or `save`).

**Can save conversations** and **Can search conversations** give or take back the Agent's [conversation archive](#conversation-archive) Grants the same way (`agentAccess` `grantConversations` and `ungrantConversations` with the Agent and `add` or `search`).

- **What it grants.** One standing `read` Grant, `<agentId>-service-<provider>`, naming exactly that Service's read targets from `SERVICE_ACTIONS` (`serviceReadTargets`): `github/list`, `github/read` and `github/search`; `posthog/query` and `posthog/read`; `cloudflare/read`. The page sends no targets. A name that is not a Service is refused, and so are an unknown or revoked Agent and a Service that is not connected. Off stamps `revokedAt` on that Grant. Revoking the Agent revokes it with the rest, and the default Grants written each run never touch it.
- **Audit.** Each change is one `agent.audit` entry: `target` is the Service, `action` is `grant` or `ungrant`, `decision` is `allowed`. The page shows it as "You let it read" or "You stopped it reading". It does not count as the Agent's last use.
- **Immediately.** The standing server reads the Agent's Grants on every call, so its next `read_service` call runs or is refused without a restart.
- **Who may call it.** These are operations of the same `agentAccess` action as Revoke, so the same pages reach them. A World page on another device does not (`agentAccess` is not in `ROOM_ALLOWED`), and no World tool does.

`node scripts/your-agent-ui-check.ts` checks the list, the Service and ask checkboxes and Revoke. `node scripts/agent-grants-check.ts` and `node scripts/harness-sessions-check.ts` check the targets, refused names, the audit, and a granted Agent's `read_service` call running on the standing server while an ungranted one is refused.

## Agent asks

An Agent can ask the person something, or leave work for an Agent to take, as an `AgentAsk` ([`contracts/agent-asks.ts`](../../contracts/agent-asks.ts)). Core decides every change ([`asks.ts`](asks.ts)); `node scripts/agent-asks-check.ts` checks it.

- **What an ask holds.** An ID the host makes, the posting Agent's `agentId` (stamped by the host from the caller's token; an `agentId` the model sends is dropped), a kind (`ask`, a question for the person, or `input`, work an Agent may take), a title (at most 200 characters, one line), a body (at most 4,000), up to 4 choices, one optional `https` link, tags, a status (`open`, `claimed`, `answered`, `done`, `skipped`), what describes each [attachment](#ask-attachments) it carries, and a revision that each change raises by one. Control characters and anything that looks like a password, token or key are refused, never stored.
- **Limits.** An Agent may have at most 20 asks open or claimed at once.
- **Reading.** An Agent reads only its own asks: the ones it posted and the ones it claimed.
- **Claiming.** Only `input` asks can be claimed, at most 10 per call. A claim holds for 60 minutes; after that, another Agent may claim the ask again.
- **Resolving.** Only the Agent holding the claim resolves an ask, with a note and `https` links, naming the revision it read. A stale revision is refused.
- **The person's answer.** One of the ask's own choices with an optional note, or Done, or Dismiss. An ask takes one answer.
- **Attention.** Each ask is an Attention item from the host's own provider `agents`, written with no model: a task when it offers choices, otherwise an update. It carries the posting Agent's ID and name, so the card says which Agent asks.
- **On the host.** Asks are the World tool `agent_asks`, as the gateway targets `asks/post`, `asks/read`, `asks/claim`, `asks/resolve` and `asks/attachment`, on the standing `worldlet` MCP server of the Electron and Node hosts alike (`agent-runtime/agent-asks.ts`). A call always goes to the Agent's own asks, under its own Grants: the host passes the Agent whose token made it, and the call never goes to a Fox turn. Fox's own turns get an error for them and talk with the person instead. Each ask and its Attention item `ask-<id>` are saved together in `world.sqlite` (`state.agent-asks`, [storage](../items/STORAGE.md)). A call outside any Fox turn never sees another Agent's ask items through `items/query`.
- **Grants.** No Agent may use asks by default, and a Fox turn's Grant never covers them. Settings › Agent › Access gives two standing Grants (`askGrant`), on the `agentAccess` action beside Revoke as `grantAsks` and `ungrantAsks`, each change audited (`grant-ask`, `ungrant-work`, …):
  - "Can ask you" (`<agentId>-asks-ask`): `asks/post`, `asks/read` and `asks/attachment`.
  - "Can take work" (`<agentId>-asks-work`): `asks/claim`, `asks/resolve` and `asks/attachment`.
  A Grant given before `asks/attachment` existed covers it too: Core reads every stored ask Grant with today's targets (`readGrant`).
  Both are `read` Grants: an ask only shows something to the person, as a draft for review does, and is not a guarded write.
- **The card.** The item is final as the host writes it (`attentionContentVersion` 1, its reason "<Agent> asks you"), so it shows in the Attention Center with no model pass. Its card ([`notion-world.ts`](../../ui/shell/notion-world.ts), [`attention-preview.ts`](../../ui/attention/attention-preview.ts)) says "<Agent> asks", shows the ask's choices as pills with an optional note (Reply when it has no choices), and its Done and Dismiss answer the ask itself (`done`, `skipped`); it also shows what the ask carries ([attachments](#ask-attachments)). The page sends only the ask's ID, the outcome, the choice and the note: never an Agent or a status. `node scripts/agent-ask-ui-check.ts` checks the card. On the phone the item shows as any other Attention item, and its Done or Dismiss settles the ask as below.
- **Answers.** The person answers with the `agentAsk` action (`answer`: the ask's ID, `answered` with one of its choices and an optional note, `done` or `skipped`). Its `answer` operation is in `ROOM_ALLOWED`, like `worldItemStatus`, so a World page on another device answers asks as it settles any item.
- **Asks that carry GitHub drafts.** An ask (not `input` work) may carry up to 10 of the posting Agent's own pending [GitHub drafts](#github-drafts) (`draftIds`); the host refuses one that is another Agent's, unknown or already settled. Such an ask always offers `Approve` (with no choices of its own: `Approve` and `Not now`), and its line on the card says "Approve writes its 2 GitHub drafts". The page sends that Approve as `agentAsk` `approveDrafts`, which is not in `ROOM_ALLOWED`: only this computer's pages may approve GitHub writes, and an `answer` of Approve on such an ask is refused with that reason. The host approves each draft still pending as on its own card (the target read again, refused when it changed, otherwise written once), then records the answer; the page says what was written. If one could not be tried (GitHub did not answer, no GitHub App), the ask stays open and Approve can be chosen again; drafts already written stay written. Any other answer, Done or Dismiss leaves the drafts unrun, still pending on their own cards. `asks/read` shows each carried draft's status, result link and why it was not written. Done or Dismiss through the item's ordinary status (`worldItemStatus`) settles the ask on its next call. Each answer is one `agent.audit` entry for the asking Agent (`answer`). `node scripts/agent-asks-host-check.ts` checks this on a real `world.sqlite` through the standing server; `harness-sessions-check` and `agent-grants-check` check the Grants.

### Ask attachments

An ask, a question or `input` work, may carry screenshots and files, so an app's feedback button or a daemon on a machine can post one with a screenshot and its logs into the person's own World rather than to an inbox elsewhere. Core checks them ([`asks.ts`](asks.ts) `readAskAttachments`); the host keeps them.

- **What may be attached.** `asks/post` takes `attachments`: each a `name`, a `type` and its bytes in base64 (`data`). Up to 8 pictures (`image/png`, `image/jpeg`, `image/webp`, `image/gif`), at most 5 MB each, and up to 12 other files (`text/plain`, `text/csv`, `application/json`, `application/zip`, `application/gzip`), at most 2 MB each; all of one ask's together at most 20 MB. Nothing that runs: any other type is refused (SVG, HTML, scripts, programs). A picture, ZIP or gzip whose first bytes are not its type's is refused, so a card never draws something that is not the picture it says it is. An empty file is refused. Every refusal says what is allowed.
- **Names.** Folders are dropped, control characters and characters a file name may not hold become `_`, a leading dot is removed, a reserved Windows name gets `_` in front, and the name ends in an extension of its own type (`run.exe` sent as `text/plain` is kept as `run.exe.txt`), at most 120 characters. A name that looks like a password, token or key is refused like any ask text.
- **Data, not instructions.** The bytes are kept exactly as sent and never scanned for secrets (logs often hold strings that look like tokens), shown to a model as instructions, rendered as markup or opened. `asks/attachment` answers mark them `untrustedContent`.
- **What the ask keeps.** Only what describes each: `id` (`att-1`, `att-2`, … in the order sent), the safe `name`, `type`, `size` and `sha256` (the host's hash of the bytes). `asks/read` and `asks/claim` return that. The bytes are saved in the same transaction as the ask, in `world.sqlite` (`agent_ask_attachments`, keyed by the ask's ID and the attachment's ID; [storage](../items/STORAGE.md)), so they travel in World backups with the rest of the World.
- **Reading the bytes.** `asks/attachment` with the ask's `id`, the `attachment` ID and an optional `offset` returns up to 96 KB (98,304 bytes) in base64, with `nextOffset` while more remain. Only the Agent that posted the ask and the Agent that claimed it may read them, under "Can ask you" or "Can take work"; to any other Agent the ask does not exist. The standing server takes calls of up to about 28 MB, room for an ask with all its attachments in base64; a Fox turn's own bridge stays at 1 MB. A larger call is refused in words.
- **On the card.** The ask's Attention item lists each attachment's `id`, name, type and size (`askAttachments`), never its bytes. Its card shows each picture as a thumbnail and names each other file with its size, whatever the ask's status. The page reads a picture with the host action `agentAsk` `attachment` (the ask's ID and the attachment's), which is not in `ROOM_ALLOWED`: a screenshot may be private, so a World page on another device shows the names only.
- **Retention.** Attachments stay with their ask: answering, Done, Dismiss, claiming and resolving keep them, and the ask keeps its record of them. No ask is removed today, so neither are its attachments; whatever removes an ask in future removes its attachments with it.

`node scripts/agent-asks-check.ts` checks the types, sizes, counts, names, signatures and who may read; `node scripts/agent-asks-host-check.ts` posts a screenshot and a log through the standing server, reads them back in parts, and checks another Agent cannot; `node scripts/agent-ask-ui-check.ts` checks the thumbnails and file names on the card.

## Agents for scripts

A daemon, a scheduled job or any other program on this computer can reach the World as an Agent of its own, with its own token, Grants and audit like any other. The person adds one by name in Settings › Agent › Access (**Add an Agent for a script**; host action `agentAccess` `addScript`, which takes only the name), or on the Node host with `worldlet register --script <name>` ([the command line](../../platform/node/README.md#the-worldlet-command)). Core checks the name (one line, at most 60 characters, no credential) and makes its ID ([`script-agents.ts`](script-agents.ts)): the name's letters and digits in lowercase, never a Harness's own ID, with a number added when it is taken. Its Harness is `script` and it runs on this computer (`local`); at most 20 may be active at once.

- **Its file.** Each run the host (desktop app and Node host alike, `agent-runtime/script-agents.ts`) writes the endpoint and that Agent's new token into `worldlet-mcp-endpoint.<agentId>.json` in the [fixed MCP home](../../platform/node/README.md#one-fixed-mcp-home) (`~/.worldlet/mcp`, or under `WORLDLET_HOME`), owner-only, and removes it on quit. Settings shows where it is. The list of these Agents is kept with Fox's setup choices (`agent_settings`, `script-agents`).
- **Calling.** The program reads `url` and `token` from that file and sends `POST <url>` with `Authorization: Bearer <token>` and the JSON body `{"method":"call","name":"call_world_tool","arguments":{"target":"agents","action":"report","arguments":"{\"status\":\"idle\"}"}}` (`describe_world_tools` lists what its Grants reach). The answer is `{"text":"<the result as JSON>","isError":false}`. An unknown or old token gets 404, as if Worldlet were closed: the program reads the file again on its next call.
- **Grants.** The default Grants of every Agent, and nothing more until the person allows it in Settings, as for any Agent.
- **Revoking.** Revoke removes its file, and it is not written again.

`node scripts/script-agents-check.ts` checks the names and IDs, the owner-only file, calls under the Agent's own Grants, a new token each run and revoking.

## Agent reports

Each Agent can say what it is doing, so the person and the other Agents in the World see who is working on what, who is free and who has gone quiet. The shapes are in [`contracts/agent-reports.ts`](../../contracts/agent-reports.ts); Core decides ([`reports.ts`](reports.ts)); `node scripts/agent-reports-check.ts` checks it.

- **What a report holds.** A status (`working`, `idle`, `blocked` or `offline`), a one-line summary (at most 280 characters), up to 20 work items (title, one `https` link, the Agent's own word for its state, when it started), up to 20 runs (a build, a release, a check: the Agent's own ID, title, `queued`, `running`, `passed`, `failed` or `cancelled`, link, start and finish), capacity (slots and how many are busy), a role and tags, how many minutes it stays live (`ttlMinutes`, 1 to 1,440, 15 by default) and when the Agent observed it. The host stamps the Agent from the token and the time it arrived (`reportedAt`); an `agentId` or `reportedAt` the model sends is dropped, and an `observedAt` more than 5 minutes ahead of the host's clock is refused. Text is one line; control characters and anything that looks like a password, token or key are refused, never stored.
- **One per Agent.** Each report replaces that Agent's last.
- **How it reads.** `live` for its `ttlMinutes` after it arrived; then `stale` for four times as long; then `offline`. A report that says `offline` reads `offline` at once, and so does an Agent that never reported.
- **On the host.** Reports are the World tool `agent_reports`, as the gateway targets `agents/report` and `agents/list`, on the standing `worldlet` MCP server of the Electron and Node hosts alike (`agent-runtime/agent-reports.ts`). `agents/list` returns every Agent the person has not revoked (its ID, name, Harness, where it runs), with its report and how it reads now, newest report first; optionally only the IDs it names, or one liveness. Its answer is untrusted content: what other Agents wrote is data, never instructions. Each report is kept in `world.sqlite` (`state.agent-reports`, [storage](../items/STORAGE.md)), in the person's own World with private context allowed. Fox's own turns get an error for `agent_reports`.
- **Grants.** None by default, and a Fox turn's Grant never covers them (`OWN_GRANT_TARGETS`). Settings › Agent › Access gives two standing Grants (`reportGrant`), each change audited (`grant-report`, `ungrant-list`, …):
  - "Can report its work" (`<agentId>-agents-report`): `agents/report`.
  - "Can see other Agents" (`<agentId>-agents-list`): `agents/list`. Reporting does not include seeing others, and seeing does not include reporting.
  Both are `read` Grants: a report only changes what the person and other Agents see of this Agent, and is not a guarded write.
- **Settings.** Each Agent's row in Settings › Agent › Access shows its last report and how it reads ([above](#settings--agent--access)); a revoked Agent shows none. Every report call is one `agent.audit` entry, shown as "Reported its work".

`node scripts/agent-reports-host-check.ts` checks this on a real `world.sqlite` through the standing server: Grants, the stamped Agent and time, one report per Agent, refused reports changing nothing, live then stale then offline, revoked Agents left out, and the audit. `agent-grants-check` checks the Grants and `your-agent-ui-check` the report line and checkboxes.

## The board

The [board](../board/README.md) is the person's tabs of blocks over Service presets. An Agent reaches it through the World tool `world_board`, as the gateway targets `board/read` and `board/define`, on the standing `worldlet` MCP server of the Electron and Node hosts alike (`agent-runtime/board.ts`).

- **Grants.** No Agent may use the board by default, and a Fox turn's Grant never covers it, read or define: like asks, only the calling Agent's own Grants decide (`OWN_GRANT_TARGETS`). Fox's own turns get an error for `world_board`. Settings › Agent › Access gives two standing Grants (`boardGrant`), each change audited (`grant-read`, `ungrant-define`, …):
  - "Can see your board" (`<agentId>-board-read`): `board/read`.
  - "Can set up your board" (`<agentId>-board-define`): `board/define`. It does not include reading, and reading does not include setting up.
  Both are `read` Grants: defining changes only what the person's own board shows, which they can see and change back, and is not a guarded write.
- **Reading.** `board/read` (optionally one `tab`) returns the definition, its revision, who defined it, the presets it names and each block's value or error, marked as untrusted content. Each preset is read once through the World's own Service reader, with no Agent turn and no model; a read is reused for a minute. A block whose Service the calling Agent's own Grants do not let it read (`read_service` would be refused) shows that on the block, and that Service is not read for it: the board never shows an Agent a Service it cannot read itself.
- **Setting up.** `board/define` replaces the whole definition and may save up to 20 Service presets with it, naming the revision it read (0 with no board yet). A stale revision is refused and the answer names the current one. Anything not valid in the definition or a preset refuses the whole call, and nothing changes. The board keeps the defining Agent's ID, stamped from its token.
- **Storage and the person.** The board is `state.board` in `world.sqlite`, saved with its presets in one transaction ([storage](../items/STORAGE.md)), in the person's own World with private context allowed. The host action `board` (`read`, optionally a `tab`) shows the person every connected Service; only `board/read` is in `ROOM_ALLOWED` for an already paired World page. This is the person’s view, not an Agent identity or a grant; Agent calls still use their own token and Service grants.
- **Audit.** Every call's decision is one `agent.audit` entry for the calling Agent, as for any World tool. `node scripts/board-host-check.ts` checks all of this on a real `world.sqlite` through the standing server; `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkboxes.

## GitHub drafts

An Agent can prepare a change on GitHub, and the person approves it on its Attention card before anything is written. The shapes are in [`contracts/github-drafts.ts`](../../contracts/github-drafts.ts); Core decides ([`github-drafts.ts`](github-drafts.ts)); the host keeps the drafts and talks to GitHub (`agent-runtime/github-drafts.ts`).

- **Writes.** `issue.create` (a new Issue in `owner/repo`: title, optional body and labels), `issue.comment` (a comment on an Issue or pull request `owner/repo#123`), `labels.add` and `labels.remove` (up to 10 labels), `issue.close` (as completed) and `issue.reopen` (an Issue only, never a pull request). Text is at most 256 characters for a title and 8,000 for a body; control characters and anything that looks like a password, token or key are refused.
- **Drafting.** The World tool `github_drafts`, as the gateway targets `github-drafts/create` and `github-drafts/read`, on the standing `worldlet` MCP server of the Electron and Node hosts alike. On `create` the host reads the target once as the GitHub App (GitHub's REST API: the Issue or pull request, or the repository for a new Issue) and keeps it with the draft: its kind, state, `updatedAt`, title and link. A write that does not fit is refused at once (closing a pull request, closing a closed Issue, anything in an archived repository, a target the App cannot see). An Agent may have at most 20 drafts pending. `read` returns only the Agent's own drafts, with their status (`pending`, `written`, `stale`, `failed`, `dismissed`), why one was not written, and the link to what was written.
- **Grants.** None by default, and a Fox turn's `*/*` Grant never covers them (`OWN_GRANT_TARGETS`); neither does Can read GitHub. **Can draft GitHub changes** (`<agentId>-github-drafts`, `githubDraftGrant`) is one standing `read` Grant naming exactly `github-drafts/create` and `github-drafts/read`: a draft only shows the person a change, and nothing reaches GitHub until they approve it. Fox's own turns get an error for `github_drafts`.
- **The card.** Each draft is an Attention task `ghd-<id>` from the host's own provider `agents`, written with no model and saved with the draft in `world.sqlite` (`state.github-drafts`, [storage](../items/STORAGE.md)). Its card ([`notion-world.ts`](../../ui/shell/notion-world.ts), [`attention-preview.ts`](../../ui/attention/attention-preview.ts)) says what it does ("Comment on example/app#12"), "<Agent> drafted this for <repo>", the exact text as plain text (never rendered), and Open on GitHub, with **Approve** and **Dismiss**. The page sends only the draft's ID to the host action `githubDraft` (`approve` or `dismiss`). `node scripts/github-draft-ui-check.ts` checks the card.
- **Approve.** The host reads the target again as the App. When it is gone (deleted, moved, or no longer visible to the App), its state changed, or (an Issue or pull request) its `updatedAt` changed, nothing is written and the draft becomes `stale` with the reason, which the card says. A repository's `updatedAt` is not compared, since stars and settings move it. Otherwise each request is made once (no retry), and the draft becomes `written` with the link GitHub answered (the new Issue or comment) or the target's, or `failed` with GitHub's words. A draft settles once: approving it again is refused. A write made after the target was read changes its `updatedAt`, so even a draft left pending by a crash mid-write is refused as stale rather than written twice (a new Issue is the exception).
- **With an ask.** An Agent can put several drafts before the person at once by posting an ask that carries them; its Approve approves them all the same way ([Agent asks](#agent-asks)).
- **Only on this computer.** `githubDraft` and `githubApp` are not in `ROOM_ALLOWED`, so a World page on another device cannot approve a GitHub write or see the App. On a phone the draft shows like any other Attention item, and its Done or Dismiss there (`worldItemStatus`) dismisses the draft: nothing is written.
- **The GitHub App.** Writes run as a GitHub App the person connects in Settings › Agent › Connections (**GitHub writes**: its App ID, installation ID and private key), so they show on GitHub as that App. The page sends them to the host action `githubApp` (`connect`) once and clears the key field at once. The host signs a JSON Web Token with the key (RS256, nine minutes), exchanges it for an installation token, and keeps the three settings in the vault (`github-app`) only if GitHub accepts them; a refused or malformed App replaces nothing. The installation token is kept in memory until a minute before it expires. The settings, the signed token and the installation token never go to a page, an Agent, an audit entry, a log or an event; `status` answers only whether an App is connected, and Disconnect forgets it.
- **Audit.** Each `create` and `read` is decided and audited like any World tool call. Each Approve is one `agent.audit` entry for the drafting Agent (`approve`, `allowed` with the result's link, or `denied` with why nothing was written), and each Dismiss is one (`dismiss`). Settings › Agent › Access shows them as "You approved its GitHub draft" and "You dismissed its GitHub draft".

`node scripts/github-drafts-host-check.ts` checks this on a real `world.sqlite` through the standing server, against a stubbed GitHub that verifies the App's signed token: Grants, drafting, each write, a changed, closed and deleted target refused, one write per Approve, Dismiss, a phone's Done, a refused write, the audit, and that the key and tokens appear in no answer, stored row, audit entry or log line. `agent-grants-check` checks the Grant and `your-agent-ui-check` the checkbox and the App's fields.

## Conversation archive

Conversations held outside Worldlet (a team chat, a project's threads, another Agent's sessions) can be saved into the World, so the person's Agents can search them later. The shapes are in [`contracts/conversations.ts`](../../contracts/conversations.ts); Core checks and cleans ([`conversations.ts`](conversations.ts)); the host keeps them (`agent-runtime/conversations.ts`).

- **Saving.** The World tool `world_conversations`, as the gateway targets `conversations/add` and `conversations/search`, on the standing `worldlet` MCP server of the Electron and Node hosts alike. `add` takes a `source` the Agent names (one line, at most 80 characters) and up to 200 messages, each with its own `id` there, a `thread`, an optional `threadTitle`, an `author` (`person`, `agent` or `system`), optional `authorName` and `surface`, `at` (an ISO time) and `text`. Saving a source's message ID again replaces it when anything changed (an edit), keeping a thread title or author name the new copy lacks; the answer counts what was `added`, `updated` and `unchanged`. A bad message refuses the whole call and nothing is kept.
- **Cleaning.** Anything that looks like a password, token, key or bearer value is replaced with `[hidden]` before it is kept (a Git commit hash stays); control characters are dropped; text past 32,000 characters is cut and ends with `[…cut]`. Text is never refused for what it holds, so one pasted key does not lose a conversation.
- **Searching.** `search` returns messages newest first with how many match: `q` matches anywhere in the text in any case and language, and `source`, `thread`, `author`, `since` and `until` narrow it (`limit` up to 50, default 20; `offset`). With no `q` it lists the newest, so `limit` 1 says how far a source has been saved. The answer is marked as untrusted content: it is what other people and Agents wrote.
- **Who saved what.** Each message keeps the Agent that saved it last (`agentId`), stamped from the token that made the call; an `agentId` the model sends is dropped.
- **Grants.** None by default, and a Fox turn's `*/*` Grant never covers them (`OWN_GRANT_TARGETS`). Settings › Agent › Access gives two standing Grants (`conversationGrant`), each change audited (`grant-add`, `ungrant-search`, …):
  - "Can save conversations" (`<agentId>-conversations-add`): `conversations/add`.
  - "Can search conversations" (`<agentId>-conversations-search`): `conversations/search`. Searching covers every saved source, whichever Agent saved it; saving does not include searching.
  Both are `read` Grants: saving only adds to the archive the person's Agents search, and is not a guarded write. Fox's own turns get an error for `world_conversations`; Fox's conversations with the person stay in `read_companion_archive`.
- **Storage.** `agent_conversations` in `world.sqlite` with a trigram search index, apart from Fox's own conversations ([storage](../items/STORAGE.md)), in the person's own World with private context allowed. The index is left out of backups and rebuilt when missing.
- **Audit.** Every call's decision is one `agent.audit` entry for the calling Agent, as for any World tool. `node scripts/conversations-host-check.ts` checks all of this on a real `world.sqlite` through the standing server; `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkboxes.

## Tracked links

The person's table of things they put out (a post, a thread, an article, a video), from draft to published: where it went, the link that counts its visitors and how many people saw it. The shapes are in [`contracts/tracked-links.ts`](../../contracts/tracked-links.ts); Core decides ([`tracked-links.ts`](tracked-links.ts)); the host keeps the rows (`agent-runtime/tracked-links.ts`).

- **A row.** An `id` the Agent or person chooses (letters, digits and `-`, at most 64, also what a tracking link carries), a title, a summary, a `type` and `channel` in the person's words (kept in lower case), a `state` (`draft`, `ready`, `published`, `dropped`), the full text, up to 8 tags, the `url` where it was published and the `trackingUrl` people follow (both https), `publishedAt`, `views` with `viewsAt`, up to 8 `media` (https links or file names), the Agent that last changed it (host-stamped) and a revision each change raises by one. Control characters (line breaks outside the text and summary) and anything that looks like a password, token or key are refused, never stored. A World keeps at most 5,000 rows.
- **Keeping.** The World tool `world_links`, as the gateway targets `links/save` and `links/read`, on the standing `worldlet` MCP server of the Electron and Node hosts alike. `save` creates or changes up to 50 rows by `id`, naming only the fields that change (a new row needs a title); `null` clears an optional field; publishing without `publishedAt` stamps it now. A row that changes nothing is left as it is. One bad row refuses the whole call, and nothing changes.
- **Reading.** `read` returns rows newest first (by when published, else made): particular `ids`, or narrowed by `state`, `channel` and `since` (`limit` up to 100). The answer is marked as untrusted content.
- **Grants.** None by default, and a Fox turn's `*/*` Grant never covers them (`OWN_GRANT_TARGETS`). Settings › Agent › Access gives two standing Grants (`linkGrant`), each change audited (`grant-read`, `ungrant-save`, …):
  - "Can see your tracked links" (`<agentId>-links-read`): `links/read`.
  - "Can keep your tracked links" (`<agentId>-links-save`): `links/save`. Keeping does not include seeing.
  Both are `read` Grants: a row only changes the person's own table, which they can see and change back, and is not a guarded write. Fox's own turns get an error for `world_links`.
- **Storage.** `state.tracked-links` in `world.sqlite`, all of one call's rows in one transaction ([storage](../items/STORAGE.md)), in the person's own World with private context allowed.
- **Audit.** Every call's decision is one `agent.audit` entry for the calling Agent. `node scripts/tracked-links-host-check.ts` checks all of this on a real `world.sqlite` through the standing server; `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkboxes.
