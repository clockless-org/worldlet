# Agent identity, Grants and audit

Every Agent that reaches the World through the `worldlet` MCP server is its own identity, with its own list of Grants and its own audit trail. Anyone running Worldlet can see which Agent did what, give one Agent more or less than another, and revoke one without touching the rest.

The shapes are in [`contracts/agent-identity.ts`](../../contracts/agent-identity.ts); the decision is in [`grants.ts`](grants.ts); `node scripts/agent-grants-check.ts` checks both.

## Identity

An `AgentIdentity` has a stable ID (lowercase letters, digits and `-`; it names the Agent's endpoint file and its ledger rows), the name the person knows it by, its Harness (`hermes`, `openclaw`, `claude-code`, `codex`, `pi` or another adapter's ID), whether it runs on this computer (`local`) or another (`remote`), when it was created and last seen, and when it was revoked. A revoked Agent's calls are denied.

## Grants

A `Grant` gives one Agent a list of World gateway `target/action` patterns (`items/query`, `items/*`, `applet:*/launch`, `*/*`; `*` matches anything, including `/`) with:

- **access**: `read` covers reads only; `write` covers reads and writes. The host says whether a call writes (the turn rule's guarded writes and the gateway's write actions).
- **duration**: `standing` runs without asking until it is revoked or expires; `once` lets reads run and sends each write to the person's approval card (Allow once or Deny).
- optional `expiresAt` and `revokedAt`: a Grant past either counts for nothing.

`grantDecision` decides one call, in this order:

1. An unknown or revoked Agent is **denied**.
2. **The turn rule comes first** ([`turn-trust.ts`](turn-trust.ts)): a write the turn has refused, because untrusted content entered it, stays refused whatever the Grants say, with the turn rule's own words. A Grant never widens what a turn may do.
3. With no active Grant of this Agent matching the call, it is **denied**. A write matched only by `read` Grants is denied.
4. A matching `standing` Grant **allows**. Under a `once` Grant a read is **allowed** and a write is **asked**.

`describe_world_tools` lists only the targets one of the Agent's Grants names (`grantCoversTarget`).

## Audit

Each decision becomes one `AgentAuditEntry` (`at`, `agentId`, `target`, `action`, `decision`: `allowed`, `denied` or `asked`, the `grantId` that decided and a short `reason`), kept in the ledger as `agent.audit`. `keepAgentAudit` keeps the newest `AGENT_AUDIT_KEEP` entries per Agent, so a busy Agent never pushes out another's history.

## Who saved what

World items, artifacts and the Attention items built from them carry an optional `agentId`: the Agent that saved them. Hosts stamp it from the token that made the call (`prepareWorldItem` and `mergeArtifact` take it as an argument). A model never sets it: an `agentId` in what a model sends is dropped, and a saved record keeps the Agent that first saved it.

## The standing MCP server

The `worldlet` MCP server registered in an Agent's profile (World tools on Hermes, [PORTABILITY.md](PORTABILITY.md#world-tools-on-hermes)) is where Grants are enforced, on the Electron host and the [Node host](../../platform/node/README.md) alike (`agent-runtime/world-tool-bridge.ts`, `agent-runtime/agent-access.ts`):

- **Its own token and endpoint file.** Each run, each Agent gets a new token, written with the endpoint to `worldlet-mcp-endpoint.<agentId>.json` in its profile (owner-only, removed on quit). Only the token's SHA-256 hash is kept, in the vault (`agent-token:<agentId>`); a call is identified by its token, and an unknown token is answered as if Worldlet were closed. Identities and Grants are kept with Fox's setup choices (`agent_settings`, `agent-access`), so they follow the World and its backups.
- **Default Grants.** An Agent's default Grants are what a call outside any Fox turn could do before Grants existed (`HERMES_CHANNEL_TOOLS` in [`hermes-server.ts`](hermes-server.ts)): a standing `read` Grant for reads and a draft for the person's review, and a standing `write` Grant for `world/link`. They are written again each run so new Applet sources are covered (`channelDefaultGrants`). Worldlet Services (`read_service`: `github/list`, `github/read`, `github/search`, [INTEGRATIONS.md](../applets/INTEGRATIONS.md#github-service); `posthog/query`, `posthog/read`, [PostHog](../applets/INTEGRATIONS.md#posthog-service); `cloudflare/read`, [Cloudflare](../applets/INTEGRATIONS.md#cloudflare-service); `http/list`, `http/read`, [HTTP JSON](../applets/INTEGRATIONS.md#http-json-service); `search-console/list`, `search-console/query`, [Search Console](../applets/INTEGRATIONS.md#search-console-service); `linear/list`, `linear/read`, `todoist/list`, `todoist/read`, `supabase/list`, `supabase/read`, [Linear, Todoist and Supabase](../applets/INTEGRATIONS.md#linear-todoist-and-supabase-as-worldlet-services)) are never in the default Grants written each run, since a Service can return other people's text or personal data: an Agent reads one only through a `serviceReadGrant`. Connecting a Service gives that Grant to the Agent Fox uses ([Settings › Connectors](#settings--connectors)); the person gives or takes it back for any Agent there or in [Settings › Agent › Access](#settings--agent--access). A call its Grant admits outside a Fox turn runs its read as the default reads do.
- **Calls.** Outside any Fox turn, a call is a turn of its own that starts untrusted (except the browser link), so the turn rule refuses its writes first. Any refusal but a revoked or unknown Agent's says what such a call may do: `HERMES_CHANNEL_READ_ONLY` for Hermes Agent, `STANDING_OUTSIDE_TURN` (which names no Hermes channel) for another Agent such as Claude Code or Codex. `channelToolReply` (Fox's module) checks the same Grants again before it runs anything. While a Fox turn holds the server, Hermes Agent's calls go to the turn as before (Fox's turns run on Hermes Agent; another Agent's calls are always its own, under its own Grants) (`foxTurnGrant`): reads run, a write the turn's own stream announced runs, and any other write goes to the approval card, which names the Agent (`asked`) (`standingCallDecision`).
- **Discovery.** `describe_world_tools` lists only the targets the Agent's Grants name (`standingActions`).
- **Audit.** Every call's decision is appended to the ledger as `agent.audit`, keyed by the Agent, and only its newest `AGENT_AUDIT_KEEP` entries stay. Last use is stamped on the identity at most once a minute.
- **Revoke.** Revoking an Agent stamps `revokedAt` on it and its Grants, deletes its token hash and removes its endpoint files, so its registered server answers that Worldlet is not open. It stays revoked across runs.
- **Upgrading.** A Hermes Agent registered before per-Agent tokens names the profile's single `worldlet-mcp-endpoint.json`. On the first run after the upgrade, Hermes Agent becomes the `hermes` identity with the default Grants, and that file holds the same token for that run. Its registered entry is outdated, so `hermes mcp add` saves the new file's path and its gateway restarts. The old file goes on quit.

Agents in the cloud reach the same server's call through [remote MCP](REMOTE-MCP.md): each connection the person allows is an Agent of its own (kind `remote`), with the same default Grants and audit.

`node scripts/harness-sessions-check.ts` checks the token, the files, migration, default Grants, discovery, audit and revoke against a fixture Hermes Agent.

## Settings › Connectors

Connecting a service in [Settings › Connectors](../applets/INTEGRATIONS.md#settings--connectors) makes a credential, and for a Worldlet Service one Grant. Reading is on by default (owner decision 2026-10-17): when a Service becomes connected, the Agent Fox uses (the one marked In use) gets that Service's `serviceReadGrant`, as if the person had ticked **Can read** for it, with the same audit entry (`serviceReadDefaults` in [`agent-runtime/service-readers.ts`](../../platform/electron/src/modules/agent-runtime/service-readers.ts)). No other Agent gets anything. The Services already connected are kept in the World's Agent settings (`service-read-defaults`), so a restart grants nothing again, a Grant the person took back stays off until the Service is disconnected and connected anew, and the first run after this change grants nothing for what was connected before it. A revoked Agent, or no Agent in use, gets nothing. Fox reads a connected service in its own turns, when the person asks, as before. Connecting with a key under Advanced or with a sign-in is the same to Grants, presets and schedules.

Under each connected Service's tile, **who may use it** says this in sentences (`connectorWhoMayUse` in [`core/accounts/connector-tiles.ts`](../accounts/connector-tiles.ts)), from `agentAccess` `serviceReaders` (the Agent in use and every other Agent not revoked, each with whether it may read the Service now):

- "Fox and Claude Code can look at your PostHog." with a checkbox, on by default. It gives or takes back that Agent's read Grant (`grantService`, `ungrantService`). With no Agent in use it reads "Fox can look at your PostHog when you ask." with no checkbox.
- "Before anything is changed, Worldlet asks you." It has no switch: an Agent's write to a service is always a draft the person approves on its card ([GitHub drafts](#github-drafts), [PostHog and Notion drafts](#posthog-and-notion-drafts)), whatever the Grants say.
- "Other Agents ask you the first time." (naming any that already may), with **Choose Agents**: one checklist of the other Agents' names, each a checkbox calling `grantService` or `ungrantService`. An Agent not chosen asks on an Attention card ([below](#when-an-agent-first-needs-a-service)).

Fine-grained Grants stay in Settings › Agent › Access. `node scripts/connector-readers-check.ts` checks the sentences and the default against a real Agent access store; `node scripts/connectors-ui-check.ts` checks the page.

## When an Agent first needs a Service

An Agent's `read_service` call on the standing server can be refused because it may not read that Service, or because the Service is not connected. Then the host asks the person once, instead of only answering with text ([`service-requests.ts`](service-requests.ts) decides; [`agent-runtime/service-requests.ts`](../../platform/electron/src/modules/agent-runtime/service-requests.ts) keeps it):

- **The card.** One Attention item from provider `agents`, written with no model, at most once a day for the same Agent and Service (`serviceRequestDue`). It is kept with its request in the World's ledger (`state.service-requests`), in the person's own World with private context allowed, as asks are.
  - "Claude Code wants to look at your PostHog." with **Allow** and **Not now**.
  - "Claude Code wants to use Cloudflare. It isn't connected yet." with **Connect Cloudflare** and **Not now**. Connect opens the Service's own sign-in (Google's for Search Console), the same as its tile in Settings › Connectors, then allows.
  - A Service that connects with a key or a code (HTTP JSON, and GitHub, whose code its tile shows) has **Open Connectors** instead, which opens Settings › Connectors, and **Allow**, which works once it is connected.
- **Allow** gives that Agent the Service's `serviceReadGrant` (`grantService`, audited as in Access). It is refused while the Service is not connected. **Not now** gives nothing; the card does not come back that day.
- **The refusal** keeps its reason and adds that Worldlet asked the person in their Attention Center (or already did), so the Agent tries again later instead of asking again itself. A revoked or unknown Agent never asks, and the reason is unchanged when no card applies.
- **Who may answer.** The host action `serviceRequest` (`allow` or `decline` with the request's ID). It is not in `ROOM_ALLOWED`, so only this computer's pages give an Agent a Grant.

`node scripts/service-requests-check.ts` checks the rules, the card's plain words and the whole path on a real ledger, Agent access store and standing server.

## Settings › Agent › Access

The Access part of Settings › Agent ([`ui/companion/agent-access.ts`](../../ui/companion/agent-access.ts), host action `agentAccess` in `agent-runtime/index.ts`) lists each Agent, the one used most recently first. For each it shows where it runs, its last use (or when it was revoked), its active Grants in plain words, and its five newest audit entries. Revoke asks once more in the page and then calls `agentAccess` `revoke`. That stamps `revokedAt`, deletes the Agent's token hash and removes its endpoint files. The page names places in the World and what was allowed. It never shows tokens, endpoints or MCP, except Remote access at its top, which shows the one address the person copies into a connector ([REMOTE-MCP.md](REMOTE-MCP.md)).

Under an Agent that is not revoked, each connected Worldlet Service has a **Can read <Service>** checkbox (Can read GitHub, PostHog, Cloudflare, HTTP JSON, Search Console). Turning it on calls `agentAccess` `grantService` with the Agent and the Service's name; turning it off calls `ungrantService`.

Under them, **Can see your board** and **Can set up your board** give or take back the Agent's [board](#the-board) Grants the same way (`agentAccess` `grantBoard` and `ungrantBoard` with the Agent and `read` or `define`).

**Can save to your Journal** and **Can read Agents' Journal artifacts** give or take back the Agent's [Journal artifact](#agent-artifacts) Grants the same way (`agentAccess` `grantArtifacts` and `ungrantArtifacts` with the Agent and `save` or `read`).

Once GitHub is connected (signed in on its tile in Settings › Connectors, or the person's own GitHub App under Advanced, [GitHub drafts](#github-drafts)), **Can draft GitHub changes** gives or takes back the Agent's GitHub draft Grant the same way (`agentAccess` `grantGithubDrafts` and `ungrantGithubDrafts` with only the Agent). While PostHog or Notion is connected, **Can draft PostHog changes** and **Can draft Notion changes** do the same for that Service's [drafts](#posthog-and-notion-drafts) (`grantServiceDrafts` and `ungrantServiceDrafts` with the Agent and the Service's name).

Under it, each [standing GitHub write](#standing-github-writes) Grant shows as **Can update Issues in example/app without asking: comment and change “state:” labels.** with **Remove** (`agentAccess` `ungrantGithubWrites` with the Agent and the repository). While a GitHub App is connected, a repository field, a choice (Comment and change labels, Comment, Change labels) and a label prefix (`state:` to start with) with **Allow** give another (`agentAccess` `grantGithubWrites` with the Agent, `repo`, `choice` and `labelPrefix`).

Under them, **Can report its work** and **Can see other Agents** give or take back the Agent's [report](#agent-reports) Grants the same way (`agentAccess` `grantReports` and `ungrantReports` with the Agent and `report` or `list`). Above its Grants, the Agent's row says what it last reported and when ("Working: Building the installer · Fix the build · reported 3 min ago"), or "Quiet" or "Offline" once its report has run out.

Under it, **Can ask you** and **Can take work** give or take back the Agent's ask Grants the same way (`agentAccess` `grantAsks` and `ungrantAsks` with the Agent and `ask` or `work`; the page sends no targets; [Agent asks](#agent-asks)). The page shows each change as "You allowed it" or "You turned it off", and an answer as "You answered its ask".

At the top of the list, **Give new work to** chooses the Agent that work posted for no Agent in particular goes to (`agentAccess` `setOrderTarget` with the Agent, or none), and under each Agent that is not revoked, **Wake it for new work** sets the program Worldlet runs to wake it (`agentAccess` `setWake` with the Agent and the command as a list of words, empty to remove it); see [Orders and waking an Agent](#orders-and-waking-an-agent).

**Can see your tracked links** and **Can keep your tracked links** give or take back the Agent's [tracked links](#tracked-links) Grants the same way (`agentAccess` `grantLinks` and `ungrantLinks` with the Agent and `read` or `save`).

**Can save conversations** and **Can search conversations** give or take back the Agent's [conversation archive](#conversation-archive) Grants the same way (`agentAccess` `grantConversations` and `ungrantConversations` with the Agent and `add` or `search`).

- **What it grants.** One standing `read` Grant, `<agentId>-service-<provider>`, naming exactly that Service's read targets from `SERVICE_ACTIONS` (`serviceReadTargets`): `github/list`, `github/read`, `github/search` and `github/releases`; `posthog/query` and `posthog/read`; `cloudflare/read`; `http/list` and `http/read` (every HTTP JSON endpoint the person connected, together); `search-console/list` and `search-console/query`; and, for every Service, `context/search` and `context/read`, the World's [saved Service context](../applets/INTEGRATIONS.md#searching-saved-service-context), whose answers hold only the Services the calling Agent may read (`serviceGrantTargets`). Only the Agent's own Grants reach `context` (`OWN_GRANT_TARGETS`), and a Fox turn reads the Service itself. The page sends no targets. A stored one counts with the Service's reads as they are now (`currentServiceGrant`, applied when Agent access loads its Grants), so "Can read GitHub" given before GitHub had `releases` covers it, with its other terms and any revocation kept. A name that is not a Service is refused, and so are an unknown or revoked Agent and a Service that is not connected. Off stamps `revokedAt` on that Grant. Revoking the Agent revokes it with the rest, and the default Grants written each run never touch it.
- **Audit.** Each change is one `agent.audit` entry: `target` is the Service, `action` is `grant` or `ungrant`, `decision` is `allowed`. The page shows it as "You let it read" or "You stopped it reading". It does not count as the Agent's last use.
- **Immediately.** The standing server reads the Agent's Grants on every call, so its next `read_service` call runs or is refused without a restart.
- **Who may call it.** These are operations of the same `agentAccess` action as Revoke, so the same pages reach them. A World page on another device does not (`agentAccess` is not in `ROOM_ALLOWED`), and no World tool does.

`node scripts/your-agent-ui-check.ts` checks the list, the Service and ask checkboxes and Revoke. `node scripts/agent-grants-check.ts` and `node scripts/harness-sessions-check.ts` check the targets, refused names, the audit, and a granted Agent's `read_service` call running on the standing server while an ungranted one is refused.

## Agent asks

An Agent can ask the person something, or leave work for an Agent to take, as an `AgentAsk` ([`contracts/agent-asks.ts`](../../contracts/agent-asks.ts)). Core decides every change ([`asks.ts`](asks.ts)); `node scripts/agent-asks-check.ts` checks it.

- **What an ask holds.** An ID the host makes, the posting Agent's `agentId` (stamped by the host from the caller's token; an `agentId` the model sends is dropped), a kind (`ask`, a question for the person, or `input`, work an Agent may take), for `input` work optionally the Agent it is for (`for`, [orders](#orders-and-waking-an-agent)), a title (at most 200 characters, one line), a body (at most 4,000), up to 4 choices, one optional `https` link, tags, a status (`open`, `claimed`, `answered`, `done`, `skipped`), what describes each [attachment](#ask-attachments) it carries, and a revision that each change raises by one. Control characters and anything that looks like a password, token or key are refused, never stored.
- **Limits.** An Agent may have at most 20 asks open or claimed at once.
- **Reading.** An Agent reads only its own asks: the ones it posted, the work that is for it and the ones it claimed.
- **Claiming.** Only `input` asks can be claimed, at most 10 per call, work for the calling Agent first. A claim holds for 60 minutes; after that, another Agent may claim the ask again. Work for one Agent waits 15 minutes for it before another may claim it.
- **Resolving.** Only the Agent holding the claim resolves an ask, with a note and `https` links, naming the revision it read. A stale revision is refused.
- **The person's answer.** One of the ask's own choices with an optional note, or Done, or Dismiss. An ask takes one answer.
- **Attention.** Each ask is an Attention item from the host's own provider `agents`, written with no model: a task when it offers choices, otherwise an update. It carries the posting Agent's ID and name, so the card says which Agent asks.
- **On the host.** Asks are the World tool `agent_asks`, as the gateway targets `asks/post`, `asks/read`, `asks/claim`, `asks/resolve` and `asks/attachment`, on the standing `worldlet` MCP server of the Electron and Node hosts alike (`agent-runtime/agent-asks.ts`). A call always goes to the Agent's own asks, under its own Grants: the host passes the Agent whose token made it, and the call never goes to a Fox turn. Fox's own turns get an error for them and talk with the person instead. Each ask and its Attention item `ask-<id>` are saved together in `world.sqlite` (`state.agent-asks`, [storage](../items/STORAGE.md)). A call outside any Fox turn never sees another Agent's ask items through `items/query`.
- **Grants.** No Agent may use asks by default, and a Fox turn's Grant never covers them. Settings › Agent › Access gives two standing Grants (`askGrant`), on the `agentAccess` action beside Revoke as `grantAsks` and `ungrantAsks`, each change audited (`grant-ask`, `ungrant-work`, …):
  - "Can ask you" (`<agentId>-asks-ask`): `asks/post`, `asks/read` and `asks/attachment`.
  - "Can take work" (`<agentId>-asks-work`): `asks/claim`, `asks/resolve` and `asks/attachment`.
  A Grant given before `asks/attachment` existed covers it too: Core reads every stored ask Grant with today's targets (`readGrant`).
  Both are `read` Grants: an ask only shows something to the person, as a draft for review does, and is not a guarded write.
- **The card.** The item is final as the host writes it (`attentionContentVersion` 1, its reason "<Agent> asks you"), so it shows in the Attention Center with no model pass. Its card ([`notion-world.ts`](../../ui/shell/notion-world.ts), [`attention-preview.ts`](../../ui/attention/attention-preview.ts)) says "<Agent> asks", shows the ask's choices as pills with an optional note (Reply when it has no choices), and its Done and Dismiss answer the ask itself (`done`, `skipped`); it also shows what the ask carries ([attachments](#ask-attachments)). The page sends only the ask's ID, the outcome, the choice and the note: never an Agent or a status. `node scripts/agent-ask-ui-check.ts` checks the card. On the phone the item shows as any other Attention item, and its Done or Dismiss settles the ask as below.
- **Answers.** The person answers with the `agentAsk` action (`answer`: the ask's ID, `answered` with one of its choices and an optional note, `done` or `skipped`). Its `answer` operation is in `ROOM_ALLOWED`, like `worldItemStatus`, so a World page on another device answers asks as it settles any item.
- **Asks that carry drafts.** An ask (not `input` work) may carry up to 10 of the posting Agent's own pending [GitHub drafts](#github-drafts) and [PostHog and Notion drafts](#posthog-and-notion-drafts) (`draftIds`); the host refuses one that is another Agent's, unknown or already settled. Such an ask always offers `Approve` (with no choices of its own: `Approve` and `Not now`), and its line on the card says "Approve writes its 2 GitHub drafts" (or names PostHog or Notion, or just "drafts" when they are of more than one Service). The page sends that Approve as `agentAsk` `approveDrafts`, which is not in `ROOM_ALLOWED`: only this computer's pages may approve these writes, and an `answer` of Approve on such an ask is refused with that reason. The host approves each draft still pending as on its own card (the target read again, refused when it changed, otherwise written once), then records the answer; the page says what was written. If one could not be tried (the Service did not answer or is not connected), the ask stays open and Approve can be chosen again; drafts already written stay written. Any other answer, Done or Dismiss leaves the drafts unrun, still pending on their own cards. `asks/read` shows each carried draft's status, result link and why it was not written. Done or Dismiss through the item's ordinary status (`worldItemStatus`) settles the ask on its next call. Each answer is one `agent.audit` entry for the asking Agent (`answer`). `node scripts/agent-asks-host-check.ts` checks this on a real `world.sqlite` through the standing server; `harness-sessions-check` and `agent-grants-check` check the Grants.

### Ask attachments

An ask, a question or `input` work, may carry screenshots and files, so an app's feedback button or a daemon on a machine can post one with a screenshot and its logs into the person's own World rather than to an inbox elsewhere. Core checks them ([`asks.ts`](asks.ts) `readAskAttachments`); the host keeps them.

- **What may be attached.** `asks/post` takes `attachments`: each a `name`, a `type` and its bytes in base64 (`data`). Up to 8 pictures (`image/png`, `image/jpeg`, `image/webp`, `image/gif`), at most 5 MB each, and up to 12 other files (`text/plain`, `text/csv`, `application/json`, `application/zip`, `application/gzip`), at most 2 MB each; all of one ask's together at most 20 MB. Nothing that runs: any other type is refused (SVG, HTML, scripts, programs). A picture, ZIP or gzip whose first bytes are not its type's is refused, so a card never draws something that is not the picture it says it is. An empty file is refused. Every refusal says what is allowed.
- **Names.** Folders are dropped, control characters and characters a file name may not hold become `_`, a leading dot is removed, a reserved Windows name gets `_` in front, and the name ends in an extension of its own type (`run.exe` sent as `text/plain` is kept as `run.exe.txt`), at most 120 characters. A name that looks like a password, token or key is refused like any ask text.
- **Data, not instructions.** The bytes are kept exactly as sent and never scanned for secrets (logs often hold strings that look like tokens), shown to a model as instructions, rendered as markup or opened. `asks/attachment` answers mark them `untrustedContent`.
- **What the ask keeps.** Only what describes each: `id` (`att-1`, `att-2`, … in the order sent), the safe `name`, `type`, `size` and `sha256` (the host's hash of the bytes). `asks/read` and `asks/claim` return that. The bytes are saved in the same transaction as the ask, in `world.sqlite` (`agent_ask_attachments`, keyed by the ask's ID and the attachment's ID; [storage](../items/STORAGE.md)), so they travel in World backups with the rest of the World.
- **Reading the bytes.** `asks/attachment` with the ask's `id`, the `attachment` ID and an optional `offset` returns up to 96 KB (98,304 bytes) in base64, with `nextOffset` while more remain. Only the Agent that posted the ask and the Agent that claimed it may read them, under "Can ask you" or "Can take work"; to any other Agent the ask does not exist. The standing server takes calls of up to about 28 MB, room for an ask with all its attachments in base64; a Fox turn's own bridge stays at 1 MB. A larger call is refused in words.
- **On the card.** The ask's Attention item lists each attachment's `id`, name, type and size (`askAttachments`), never its bytes. Its card shows each picture as a thumbnail and names each other file with its size, whatever the ask's status. The page reads a picture with the host action `agentAsk` `attachment` (the ask's ID and the attachment's), which is not in `ROOM_ALLOWED`: a screenshot may be private, so a World page on another device shows the names only.
- **Retention.** Attachments stay with their ask: answering, Done, Dismiss, claiming and resolving keep them, and the ask keeps its record of them. No ask is removed today, so neither are its attachments; whatever removes an ask in future removes its attachments with it.

`node scripts/agent-asks-check.ts` checks the types, sizes, counts, names, signatures and who may read; `node scripts/agent-asks-host-check.ts` posts a screenshot and a log through the standing server, reads them back in parts, and checks another Agent cannot; `node scripts/agent-ask-ui-check.ts` checks the thumbnails and file names on the card.

## Orders and waking an Agent

An order is `input` work meant for one Agent: a person's request relayed by a chat bridge, a queue on another machine, an Agent handing work to another. It is an ask like any other, under the same Grants, limits and audit ([Agent asks](#agent-asks)); by convention its tags include `order`. Core decides ([`asks.ts`](asks.ts), [`orders.ts`](orders.ts)); the host keeps the setting and runs the wake (`agent-runtime/agent-orders.ts`, on the Electron and Node hosts alike). The shapes are `for` on `AgentAsk` and `AgentOrders` in [`contracts/agent-asks.ts`](../../contracts/agent-asks.ts).

- **Naming the Agent.** `asks/post` with `kind` `input` may name `for`: one Agent ID. Core refuses an Agent that is not one of this World's, or was revoked ("The Agent this work is for is not one of this World's Agents, or it was revoked."), and `for` on a question for the person.
- **Give new work to.** The person may choose one Agent in Settings › Agent › Access (the World's order target). Work posted naming no Agent is for it, unless the posting Agent is that Agent itself, the target was revoked, or the ask is a question. A named Agent always wins.
- **What changes for the Agent it is for.** It reads the work with `asks/read` (and its [attachments](#ask-attachments)), and `asks/claim` gives it work for it first. For 15 minutes (`AGENT_ASK_LIMITS.forMinutes`) after the work was posted no other Agent may claim it, named by ID or not; after that, or once a claim on it ran out, any Agent with **Can take work** may, as for any work. Nothing else changes: the Agent claims, resolves and is audited as for any ask. Its Attention card says "<Agent> left work for <Agent>".
- **Waking it.** Under each Agent the person may type a **wake command**: the full path of a program, then one argument per line. When work is posted for that Agent (named, or by the order target) by another Agent, the host runs that program, and the woken Agent claims the work with `asks/claim` as usual. A wake starts nothing else: what the program does (start a session, send a message to a machine) is the person's own choice.
  - **Only what the person typed.** The page sends the command as a list of words, never a line for a shell. The host checks it (`readWakeCommand`): the program is an absolute path (`/usr/local/bin/wake-agent`, `C:\Tools\wake.exe`), at most 16 arguments of at most 500 characters each, no control characters or line breaks, nothing that looks like a password, token or key; each refusal says what is allowed. The program runs directly, with no shell: nothing is expanded, joined or split. One placeholder exists: an argument that is exactly `{askId}` becomes the work's ID; `{askId}` inside a longer argument stays as typed, and the program is never the placeholder. No Agent, World tool or page on another device can set or change a wake command (`agentAccess` is not in `ROOM_ALLOWED`), and an Agent's own work for itself never wakes it (Fox's own turns cannot post asks at all, so they never wake one).
  - **How it runs.** Detached in the person's home folder with Worldlet's environment, stdin and output ignored, and stopped (with what it started, on macOS and Linux) if it still runs after 5 minutes. Its output is never kept: the Agent's audit gets one `wake` entry saying how it ended ("Woken for work <id>: exited with 0.", "stopped after 5 minutes", "could not start: …"), shown in Settings as "Woken for new work · Exited with 0". A program still running when Worldlet quits is left to end.
  - **At most once a minute.** An Agent is woken at most once per 60 seconds. Work posted for it in that minute wakes it once more when the minute ends, with the newest work's ID; a woken Agent should claim everything waiting for it.
- **The setting.** `agent-orders` in `agent_settings` in `world.sqlite` ([storage](../items/STORAGE.md)), so it follows the World and its backups. Setting or removing a wake command and choosing the order target are each one `agent.audit` entry for the Agent (`set-wake`, `clear-wake`, `order-target`, `clear-order-target`), shown as "Waking it for new work · You set it" and "Getting new work · You chose it". Revoking an Agent removes its wake command and clears it as the order target.

This runs a program on the person's computer: Worldlet never chooses one, and it runs only the one the person typed in Settings for that Agent. `node scripts/agent-asks-check.ts` checks `for`, the order target, the claiming wait and the command rules; `node scripts/agent-asks-host-check.ts` runs a real wake (a small Node script given the work's ID) through the standing server, with the debounce, the timeout, a program that cannot start and refused commands; `node scripts/your-agent-ui-check.ts` checks the setting and the wake command in Settings.

## Agents for scripts

A daemon, a scheduled job or any other program on this computer can reach the World as an Agent of its own, with its own token, Grants and audit like any other. The person adds one by name in Settings › Agent › Access (**Add an Agent for a script**; host action `agentAccess` `addScript`, which takes only the name), or on the Node host with `worldlet register --script <name>` ([the command line](../../platform/node/README.md#the-worldlet-command)). Core checks the name (one line, at most 60 characters, no credential) and makes its ID ([`script-agents.ts`](script-agents.ts)): the name's letters and digits in lowercase, never a Harness's own ID, with a number added when it is taken. Its Harness is `script` and it runs on this computer (`local`); at most 20 may be active at once.

A program on another computer has no file here: it uses a [remote token](REMOTE-MCP.md#a-token-for-a-script-or-another-computer) instead (`worldlet remote token <name>`).

- **Its file.** Each run the host (desktop app and Node host alike, `agent-runtime/script-agents.ts`) writes the endpoint and that Agent's new token into `worldlet-mcp-endpoint.<agentId>.json` in the [fixed MCP home](../../platform/node/README.md#one-fixed-mcp-home) (`~/.worldlet/mcp`, or under `WORLDLET_HOME`), owner-only, and removes it on quit. Settings shows where it is. The list of these Agents is kept with Fox's setup choices (`agent_settings`, `script-agents`).
- **Calling.** The program reads `url` and `token` from that file and sends `POST <url>` with `Authorization: Bearer <token>` and the JSON body `{"method":"call","name":"call_world_tool","arguments":{"target":"agents","action":"report","arguments":"{\"status\":\"idle\"}"}}` (`describe_world_tools` lists what its Grants reach). The answer is `{"text":"<the result as JSON>","isError":false}`. An unknown or old token gets 404, as if Worldlet were closed: the program reads the file again on its next call.
- **Grants.** The default Grants of every Agent, and nothing more until the person allows it in Settings, as for any Agent.
- **Revoking.** Revoke removes its file, and it is not written again.

`node scripts/script-agents-check.ts` checks the names and IDs, the owner-only file, calls under the Agent's own Grants, a new token each run and revoking.

## Agent reports

Each Agent can say what it is doing, so the person and the other Agents in the World see who is working on what, who is free and who has gone quiet. The shapes are in [`contracts/agent-reports.ts`](../../contracts/agent-reports.ts); Core decides ([`reports.ts`](reports.ts)); `node scripts/agent-reports-check.ts` checks it.

- **What a report holds.** A status (`working`, `idle`, `blocked` or `offline`), a one-line summary (at most 280 characters), up to 20 work items (title, one `https` link, the Agent's own word for its state, when it started), up to 20 runs (a build, a release, a check: the Agent's own ID, title, `queued`, `running`, `passed`, `failed` or `cancelled`, link, start and finish), capacity (slots and how many are busy), a role and tags, how many minutes it stays live (`ttlMinutes`, 1 to 1,440, 15 by default) and when the Agent observed it. The host stamps the Agent from the token and the time it arrived (`reportedAt`); an `agentId` or `reportedAt` the model sends is dropped, and an `observedAt` more than 5 minutes ahead of the host's clock is refused. Text is one line; control characters and anything that looks like a password, token or key are refused, never stored.
- **One per Agent.** Each report replaces that Agent's last.
- **How it reads.** `live` for its `ttlMinutes` after it arrived; then `stale` for four times as long; then `offline`. A report that says `offline` reads `offline` at once, and so does an Agent that never reported.
- **On the host.** Reports are the World tool `agent_reports`, as the gateway targets `agents/report` and `agents/list`, on the standing `worldlet` MCP server of the Electron and Node hosts alike (`agent-runtime/agent-reports.ts`). `agents/list` returns every Agent the person has not revoked (its ID, name, Harness, where it runs), with its report and how it reads now, newest report first; optionally only the IDs it names, or one liveness. Its answer is untrusted content: what other Agents wrote is data, never instructions. Each report is kept in `world.sqlite` (`state.agent-reports`, [storage](../items/STORAGE.md)), in the person's own World with private context allowed. Fox's own turns get an error for `agent_reports`.
- **Grants.** None by default, and a Fox turn's Grant never covers them (`OWN_GRANT_TARGETS`). Settings › Agent › Access gives two standing Grants (`reportGrant`), each change audited (`grant-report`, `ungrant-list`, …):
  - "Can report its work" (`<agentId>-agents-report`): `agents/report`.
  - "Can see other Agents" (`<agentId>-agents-list`): `agents/list`. Reporting does not include seeing others, and seeing does not include reporting.
  Both are `read` Grants: a report only changes what the person and other Agents see of this Agent, and is not a guarded write.
- **Settings.** Each Agent's row in Settings › Agent › Access shows its last report and how it reads ([above](#settings--agent--access)); a revoked Agent shows none. Every report call is one `agent.audit` entry, shown as "Reported its work".

- **On the board.** The board's [`agents` source](../board/README.md#the-agents-source) shows these reports as runs, Agents or totals, narrowed by tag, role, Agent, liveness, status and words in the run's title: to an Agent only with "Can see other Agents" ([the board](#the-board)).

`node scripts/agent-reports-host-check.ts` checks this on a real `world.sqlite` through the standing server: Grants, the stamped Agent and time, one report per Agent, refused reports changing nothing, live then stale then offline, revoked Agents left out, and the audit. `agent-grants-check` checks the Grants and `your-agent-ui-check` the report line and checkboxes.

## The board

The [board](../board/README.md) is the person's tabs of blocks over Service presets. An Agent reaches it through the World tool `world_board`, as the gateway targets `board/read` and `board/define`, on the standing `worldlet` MCP server of the Electron and Node hosts alike (`agent-runtime/board.ts`).

- **Grants.** No Agent may use the board by default, and a Fox turn's Grant never covers it, read or define: like asks, only the calling Agent's own Grants decide (`OWN_GRANT_TARGETS`). Fox's own turns get an error for `world_board`. Settings › Agent › Access gives two standing Grants (`boardGrant`), each change audited (`grant-read`, `ungrant-define`, …):
  - "Can see your board" (`<agentId>-board-read`): `board/read`.
  - "Can set up your board" (`<agentId>-board-define`): `board/define`. It does not include reading, and reading does not include setting up.
  Both are `read` Grants: defining changes only what the person's own board shows, which they can see and change back, and is not a guarded write.
- **Reading.** `board/read` (optionally one `tab`) returns the definition, its revision, who defined it, the presets it names and each block's value or error, marked as untrusted content. Each preset is read once through the World's own Service reader, with no Agent turn and no model; a read is reused for a minute. A block whose Service the calling Agent's own Grants do not let it read (`read_service` would be refused) shows that on the block, and that Service is not read for it: the board never shows an Agent a Service it cannot read itself.
- **The Agents' reports.** A block of the board's [`agents` source](../board/README.md#the-agents-source) shows what `agents/list` returns. "Can see your board" alone does not show it: the calling Agent also needs its own "Can see other Agents" (`agents/list`, decided as its own `agent_reports` call would be); without it the block says so and no report is read for it. The person's own board, and a paired World page's `board/read`, show every Agent's report, as Settings › Agent › Access does; `agents/list` itself stays out of `ROOM_ALLOWED`.
- **Setting up.** `board/define` replaces the whole definition and may save up to 20 Service presets with it, naming the revision it read (0 with no board yet). A stale revision is refused and the answer names the current one. Anything not valid in the definition or a preset refuses the whole call, and nothing changes. The board keeps the defining Agent's ID, stamped from its token.
- **Storage and the person.** The board is `state.board` in `world.sqlite`, saved with its presets in one transaction ([storage](../items/STORAGE.md)), in the person's own World with private context allowed. The host action `board` (`read`, optionally a `tab`) shows the person every connected Service; only `board/read` is in `ROOM_ALLOWED` for an already paired World page. This is the person’s view, not an Agent identity or a grant; Agent calls still use their own token and Service grants.
- **Audit.** Every call's decision is one `agent.audit` entry for the calling Agent, as for any World tool. `node scripts/board-host-check.ts` checks all of this on a real `world.sqlite` through the standing server; `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkboxes.

## GitHub drafts

An Agent can prepare a change on GitHub, and the person approves it on its Attention card before anything is written. The shapes are in [`contracts/github-drafts.ts`](../../contracts/github-drafts.ts); Core decides ([`github-drafts.ts`](github-drafts.ts)); the host keeps the drafts and talks to GitHub (`agent-runtime/github-drafts.ts`).

- **Writes.** `issue.create` (a new Issue in `owner/repo`: title, optional body and labels), `issue.comment` (a comment on an Issue or pull request `owner/repo#123`), `labels.add` and `labels.remove` (up to 10 labels), `labels.set` (below), `issue.close` (as completed) and `issue.reopen` (an Issue only, never a pull request). Text is at most 256 characters for a title and 8,000 for a body; control characters and anything that looks like a password, token or key are refused.
- **A label transition.** `labels.set` takes `expected`, the labels the Agent read, and `set`, what they become (each up to 10, either may be empty, not the same), and optionally a `prefix` (at most 49 characters): then only labels starting with it count, and every label in `expected` and `set` must start with it. `{prefix:'state:',expected:['state:queued'],set:['state:running']}` says "its `state:` labels must be exactly `state:queued`, and become `state:running`". Labels compare case-insensitively, as on GitHub. The draft is refused at once when the target's labels under the prefix are not exactly `expected`, and so is Approve (as stale, the card saying which labels it has now). Otherwise it adds what is in `set` and not `expected`, then removes what is in `expected` and not `set` (a label already gone counts as removed), and touches no other label. GitHub has no compare-and-set for labels: the check is the read made right before writing, and adding before removing means a transition cut short leaves both labels, which the next transition's check refuses, rather than none.
- **Drafting.** The World tool `github_drafts`, as the gateway targets `github-drafts/create` and `github-drafts/read`, on the standing `worldlet` MCP server of the Electron and Node hosts alike. On `create` the host reads the target once as whoever writes (below; GitHub's REST API: the Issue or pull request, or the repository for a new Issue) and keeps it with the draft: its kind, state, `updatedAt`, title and link. A write that does not fit is refused at once (closing a pull request, closing a closed Issue, anything in an archived repository, a target the App cannot see). An Agent may have at most 20 drafts pending. `read` returns only the Agent's own drafts, with their status (`pending`, `written`, `stale`, `failed`, `unknown`, `dismissed`), why one was not written (or which part of it was not), and the link to what was written.
- **Grants.** None by default, and a Fox turn's `*/*` Grant never covers them (`OWN_GRANT_TARGETS`); neither does Can read GitHub. **Can draft GitHub changes** (`<agentId>-github-drafts`, `githubDraftGrant`) is one standing `read` Grant naming exactly `github-drafts/create` and `github-drafts/read`: a draft only shows the person a change, and nothing reaches GitHub until they approve it. Fox's own turns get an error for `github_drafts`.
- **The card.** Each draft is an Attention task `ghd-<id>` from the host's own provider `agents`, written with no model and saved with the draft in `world.sqlite` (`state.github-drafts`, [storage](../items/STORAGE.md)). Its card ([`notion-world.ts`](../../ui/shell/notion-world.ts), [`attention-preview.ts`](../../ui/attention/attention-preview.ts)) says what it does ("Comment on example/app#12"), "<Agent> drafted this for <repo>", the exact text as plain text (never rendered), and Open on GitHub, with **Approve** and **Dismiss**. The page sends only the draft's ID to the host action `githubDraft` (`approve` or `dismiss`). `node scripts/github-draft-ui-check.ts` checks the card.
- **Approve.** The host reads the target again as whoever writes. When it is gone (deleted, moved, or no longer visible to the App), its state changed, or (an Issue or pull request) its `updatedAt` changed, nothing is written and the draft becomes `stale` with the reason, which the card says. A repository's `updatedAt` is not compared, since stars and settings move it. Otherwise each request is made once (no retry), and the draft becomes `written` with the link GitHub answered (the new Issue or comment) or the target's, or `failed` with GitHub's words. Each label of `labels.remove` is its own request: when GitHub removes some and refuses others, the draft is `written` with a reason naming which were removed and which are still there; when it refuses all, `failed`. A write GitHub never answered is `unknown` (check GitHub). A draft settles once: approving it again is refused. A write made after the target was read changes its `updatedAt`, so even a draft left pending by a crash mid-write is refused as stale rather than written twice. A new Issue is the exception, so its draft records `writeStartedAt` before the request is made. Approving a draft that has begun but never settled (Worldlet stopped mid-write, or GitHub did not answer) posts nothing: the host lists the repository's Issues since a minute before the write began and, if one has the draft's exact title, was made by the GitHub App and was made within ten minutes of that start, the draft becomes `written` with its link; otherwise it becomes `unknown` with a reason saying to check GitHub. Dismissing such a draft, on this computer or through its card's status, makes it `unknown` too, never "nothing was written".
- **With an ask.** An Agent can put several drafts before the person at once by posting an ask that carries them; its Approve approves them all the same way ([Agent asks](#agent-asks)).
- **Only on this computer.** `githubDraft` and `githubApp` are not in `ROOM_ALLOWED`, so a World page on another device cannot approve a GitHub write or see the App. On a phone the draft shows like any other Attention item, and its Done or Dismiss there (`worldItemStatus`) dismisses the draft: nothing is written.
- **Who writes.** By default the person, through their GitHub sign-in on the GitHub tile in Settings › Connectors (the official Worldlet GitHub App's device code, [GitHub sign-in](../applets/INTEGRATIONS.md#github-sign-in)): its user token, kept in the vault with the sign-in (`mcp:github`) and renewed with the public client ID alone, reads and writes as the person, limited to what they may do and the repositories they chose, and GitHub shows each write as made by them through Worldlet. A pasted key (Advanced › Connect with a key) only reads. A new Issue's or comment's body ends with one line naming the Agent that drafted it, "_Drafted by Claude Code in Worldlet_" (`githubDraftSignature`: the Agent's label in plain words, so it cannot add a link or a mention). A 401 renews the token once; a sign-in GitHub no longer accepts says to connect GitHub again. The user token never goes to a page, an Agent, an audit entry, a log or an event.
- **Your own GitHub App (Advanced).** Writes run as a GitHub App the person connects in Settings › Connectors › Advanced (**Your own GitHub App**: its App ID, installation ID and private key), so they show on GitHub as that App instead of the person; while one is connected it writes every approved draft. The page sends them to the host action `githubApp` (`connect`) once and clears the key field at once. The host signs a JSON Web Token with the key (RS256, nine minutes), exchanges it for an installation token, and keeps the three settings in the vault (`github-app`) only if GitHub accepts them; a refused or malformed App replaces nothing. The installation token is kept in memory until a minute before it expires. The settings, the signed token and the installation token never go to a page, an Agent, an audit entry, a log or an event; `status` answers only whether an App is connected, and Disconnect forgets it.
- **Audit.** Each `create` and `read` is decided and audited like any World tool call. Each Approve is one `agent.audit` entry for the drafting Agent (`approve`, `allowed` with the result's link, or `denied` with why nothing was written), and each Dismiss is one (`dismiss`). Settings › Agent › Access shows them as "You approved its GitHub draft" and "You dismissed its GitHub draft".

`node scripts/github-drafts-host-check.ts` checks this on a real `world.sqlite` through the standing server, against a stubbed GitHub that verifies the App's signed token: Grants, drafting, each write, a label transition and its stale labels, a changed, closed and deleted target refused, one write per Approve, Dismiss, a phone's Done, a refused write, removing some labels but not others, a new Issue begun but not seen to finish (found on GitHub, or unknown, never posted twice), the audit, and that the key and tokens appear in no answer, stored row, audit entry or log line. `agent-grants-check` checks the Grant and `your-agent-ui-check` the checkbox and the App's fields.

## Standing GitHub writes

An Agent that keeps GitHub Issues moving (a machine that takes queued work, labels it running and comments on progress) should not need the person to approve every step. The person can let one Agent make a few kinds of write on one repository without a card; everything else stays a [GitHub draft](#github-drafts). The shapes are in [`contracts/github-drafts.ts`](../../contracts/github-drafts.ts) (`GithubWriteScope`, `GithubWriteRun`); Core decides ([`github-drafts.ts`](github-drafts.ts), [`grants.ts`](grants.ts)); the host runs them in the same module as drafts (`agent-runtime/github-drafts.ts`), as the same GitHub App.

- **The Grant.** "Can update Issues in `owner/repo` without asking" (`githubWriteGrant`, ID `<agentId>-github-writes-<owner/repo>`): one standing `write` Grant naming exactly `github-writes/run`, with its reach kept on the Grant (`github`: the repository, the writes, the label prefix). The person chooses `comment` (`issue.comment`), `labels` (`labels.set` under one label prefix) or `comment-labels` (both). The page sends only the Agent, the repository, the choice and the prefix; Core builds the Grant, and refuses any other choice, a repository that is not `owner/repo` and a prefix that is empty or more than one line. One per repository (choosing again replaces it), at most 10 per Agent. Giving one needs the person's own GitHub App (Advanced). Never `issue.create`, `issue.close`, `issue.reopen` or `labels.add`/`labels.remove`, never part of the default Grants, and a Fox turn's Grant never covers it (`OWN_GRANT_TARGETS`); neither do Can read GitHub and Can draft GitHub changes, which are `read` Grants (`worldCallWrites` counts `github_writes` as a write). Fox's own turns get an error for `github_writes`. A stored Grant whose reach is not valid is dropped, not widened.
- **A call.** The World tool `github_writes`, as the gateway target `github-writes/run`, on the standing `worldlet` MCP server of the Electron and Node hosts alike, with `write` (`issue.comment` with `body`, or `labels.set` with `prefix`, `expected` and `set`, as for a draft), `target` (`owner/repo#123`), and optionally `expectedState` and `expectedUpdatedAt` as the Agent read them. Its arguments are checked as a draft's are: the same limits, no control characters, nothing that looks like a password, token or key. Then the host finds the Agent's Grant whose reach covers this repository (case-insensitive), this write and, for `labels.set`, a prefix that starts with the Grant's own; with none, nothing is read or written and the Agent is told to draft it instead. Then it reads the Issue or pull request as the App, right before writing, and refuses when it is gone, when its state or `updatedAt` is not the one the Agent named, or (`labels.set`) when its labels under the prefix are not exactly `expected`: nothing is written, and the answer says why and what it is now (state, `updatedAt`, title, link, labels). Otherwise each request is made once, as on Approve, and the answer is the link (the new comment, or the Issue). Two calls on the same Issue never overlap: the second is refused until the first ends.
- **The turn rule.** It comes first here as for every call (`standingCallDecision`). `github_writes` is not one of its guarded World writes: a call outside any Fox turn is a turn of its own that has always read GitHub's untrusted text, so the turn rule alone would refuse every one. What limits it instead is that the person named the Agent, the repository and the writes beforehand, and each write is checked against what the Agent read. Its answers carry GitHub's text and are untrusted content for any turn that sees them.
- **Audit.** Each call is two `agent.audit` entries for the Agent: the gateway's decision (`github-writes`, `run`) and what came of it (`write`: `allowed` with the result's link, or `denied` with why nothing was written, a call no Grant's reach covers included). Giving and removing one are `grant` and `ungrant`. Settings › Agent › Access shows them as "Change on GitHub without asking · Allowed", "Changed GitHub without asking · Written" or "Not written", and "Updating GitHub Issues without asking · You allowed it" or "You removed it".
- **Only as your own GitHub App.** A standing write runs only while the person's own GitHub App is connected (Advanced): through the GitHub sign-in every write is a draft the person approves first, so a call is refused, audited, and told to draft instead.
- **Revoke.** Revoking the Agent revokes these with its other Grants; disconnecting the GitHub App stops every write (the call says the App is needed), and Settings then offers no Allow but still lists the Grants to remove.

`node scripts/github-drafts-host-check.ts` checks this through the standing server against the stubbed GitHub: no Grant, another repository, a write or prefix outside the reach and another Agent's Grant all refused with nothing read; a comment and a state transition written once as the App; stale labels, state and `updatedAt` refused with nothing written; the audit. `agent-grants-check` checks the Grant, its reach and the decision; `your-agent-ui-check` the list, Allow and Remove.

## PostHog and Notion drafts

An Agent can prepare a change in PostHog or Notion the same way as a [GitHub draft](#github-drafts): the person approves it on its Attention card before anything is written. The shapes are in [`contracts/service-drafts.ts`](../../contracts/service-drafts.ts); Core decides and plans each request ([`service-drafts.ts`](service-drafts.ts)); the host keeps the drafts and makes the requests (`agent-runtime/service-drafts.ts`).

- **Writes.** PostHog: `annotation.create` (an annotation in the connected project: `content` up to 400 characters, `date` as ISO 8601 for its date marker, optional `scope` `project` or `organization`) and `flag.set` (turn an existing feature flag on or off: `target` its key or ID, `active` true or false). Notion: `page.create` (a new page in a database or under a parent page, `target` its URL or ID: a `title` up to 200 characters and optional paragraphs in `body`) and `page.append` (paragraphs added to the end of a page, `body` up to 8,000 characters). Control characters and anything that looks like a password, token or key are refused. A PostHog connected by its own sign-in asks only to read. The first PostHog draft the person approves opens PostHog's sign-in once more for its write list ([PostHog](../applets/INTEGRATIONS.md#posthog-service)), so a change is asked for twice: on the card, then on PostHog's own page.
- **Drafting.** The World tool `service_drafts`, as the gateway targets `posthog-drafts/create` and `posthog-drafts/read`, and `notion-drafts/create` and `notion-drafts/read`, on the standing `worldlet` MCP server of the Electron and Node hosts alike. On `create` the host reads the target once through the World's own connection (PostHog's API with the connected personal API key; Notion's `notion-fetch` over the World's Notion connection) and keeps it with the draft: its kind, state, last change, title and link. A write that does not fit is refused at once (a flag already on or off as asked, paragraphs for a database, a target the connection cannot see). An Agent may have at most 20 PostHog and Notion drafts pending. `read` returns only the Agent's own drafts of that Service, with their status (`pending`, `written`, `stale`, `failed`, `dismissed`), why one was not written, and the link to what was written.
- **Grants.** None by default, and a Fox turn's `*/*` Grant never covers them (`OWN_GRANT_TARGETS`); neither does Can read PostHog, nor one Service's draft Grant for the other. **Can draft PostHog changes** and **Can draft Notion changes** (`<agentId>-posthog-drafts`, `<agentId>-notion-drafts`, `serviceDraftGrant`) are each one standing `read` Grant naming exactly that Service's `create` and `read`. Settings › Agent › Access shows each only while that Service is connected. Fox's own turns get an error for `service_drafts`.
- **The card.** Each draft is an Attention task `svd-<id>` from the host's own provider `agents`, written with no model and saved with the draft in `world.sqlite` (`state.service-drafts`, [storage](../items/STORAGE.md)). Its card says what it does ("Turn on the feature flag new-checkout"), "<Agent> drafted this for PostHog · new-checkout", exactly what will be written as plain text (never rendered), and Open in PostHog or Open in Notion, with **Approve** and **Dismiss**. The page sends only the draft's ID to the host action `serviceDraft` (`approve` or `dismiss`). `node scripts/service-draft-ui-check.ts` checks the card.
- **Approve.** The host reads the target again. When it is gone, a flag's state changed, or (a flag or an appended page) its last change moved (a flag's `updated_at`; a page's last edit time, or a fingerprint of its content when Notion gives none), nothing is written and the draft becomes `stale` with the reason, which the card says. A project, a parent page or a database that takes a new page only has to still be there. Otherwise the request is made once (no retry) and the draft becomes `written` with the link to the target or the new page, or `failed` with the Service's words. A PostHog key that is refused for lacking the write scope fails the draft with a plain reason naming the scope it needs (`annotation:write` or `feature_flag:write`). A write that was sent and not answered is `failed` as possibly made. A draft settles once.
- **With an ask.** An ask can carry PostHog and Notion drafts beside GitHub ones; its Approve approves them all ([Agent asks](#agent-asks)).
- **Only on this computer.** `serviceDraft` is not in `ROOM_ALLOWED`. On a phone the draft shows like any other Attention item, and its Done or Dismiss there dismisses the draft: nothing is written.
- **Keys.** PostHog writes use the PostHog Service's personal API key and Notion writes the World's Notion connection; neither ever goes to a page, an Agent, an audit entry, a log or an event.
- **Audit.** Each Approve is one `agent.audit` entry for the drafting Agent under `posthog-drafts` or `notion-drafts` (`approve`, `allowed` with the result's link, or `denied` with why nothing was written), and each Dismiss is one (`dismiss`). Settings › Agent › Access shows them as "You approved its PostHog draft", "You dismissed its Notion draft" and so on.

`node scripts/service-drafts-host-check.ts` checks this on a real `world.sqlite` through the standing server, against a stubbed PostHog API and a stubbed Notion MCP server: Grants, drafting, each write, a changed and a deleted target refused, a missing scope, Dismiss, a phone's Done, an ask carrying both kinds, the audit, and that the key appears in no answer, stored row, audit entry or log line. `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkbox.

## Conversation archive

Conversations held outside Worldlet (a team chat, a project's threads, another Agent's sessions) can be saved into the World, so the person's Agents can search them later. The shapes are in [`contracts/conversations.ts`](../../contracts/conversations.ts); Core checks and cleans ([`conversations.ts`](conversations.ts)); the host keeps them (`agent-runtime/conversations.ts`).

- **Saving.** The World tool `world_conversations`, as the gateway targets `conversations/add` and `conversations/search`, on the standing `worldlet` MCP server of the Electron and Node hosts alike. `add` takes a `source` the Agent names (one line, at most 80 characters) and up to 200 messages, each with its own `id` there, a `thread`, an optional `threadTitle`, an `author` (`person`, `agent` or `system`), optional `authorName` and `surface`, `at` (an ISO time) and `text`. Saving a source's message ID again replaces it when anything changed (an edit), keeping a thread title or author name the new copy lacks; the answer counts what was `added`, `updated` and `unchanged`. A bad message refuses the whole call and nothing is kept.
- **Cleaning.** Anything that looks like a password, token, key or bearer value is replaced with `[hidden]` before it is kept (a Git commit hash stays); control characters are dropped; text past 32,000 characters is cut and ends with `[…cut]`. Text is never refused for what it holds, so one pasted key does not lose a conversation.
- **Searching.** `search` returns messages newest first with how many match: `q` matches anywhere in the text in any case and language, and `source`, `thread`, `author`, `since` and `until` narrow it (`limit` up to 50, default 20; `offset`). With no `q` it lists the newest, so `limit` 1 says how far a source has been saved. The answer is marked as untrusted content: it is what other people and Agents wrote.
- **Who saved what.** Each message keeps the Agent that saved it last (`agentId`), stamped from the token that made the call; an `agentId` the model sends is dropped.
- **Grants.** None by default, and a Fox turn's `*/*` Grant never covers them (`OWN_GRANT_TARGETS`). Settings › Agent › Access gives two standing Grants (`conversationGrant`), each change audited (`grant-add`, `ungrant-search`, …):
  - "Can save conversations" (`<agentId>-conversations-add`): `conversations/add`.
  - "Can search conversations" (`<agentId>-conversations-search`): `conversations/search`. Searching covers every saved source, whichever Agent saved it; saving does not include searching.
  Both are `read` Grants: saving only adds to the archive the person's Agents search, and is not a guarded write. Fox's own turns get an error for `world_conversations`; Fox's conversations with the person stay in `read_companion_archive`.
- **Storage.** `agent_conversations` in `world.sqlite` with a trigram search index, apart from Fox's own conversations ([storage](../items/STORAGE.md)), in the person's own World with private context allowed. The index is left out of backups and rebuilt when missing.
- **Audit.** Every call's decision is one `agent.audit` entry for the calling Agent, as for any World tool. `node scripts/conversations-host-check.ts` checks all of this on a real `world.sqlite` through the standing server; `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkboxes.

## Tracked links

The person's table of things they put out (a post, a thread, an article, a video), from draft to published: where it went, the link that counts its visitors and how many people saw it. The shapes are in [`contracts/tracked-links.ts`](../../contracts/tracked-links.ts); Core decides ([`tracked-links.ts`](tracked-links.ts)); the host keeps the rows (`agent-runtime/tracked-links.ts`).

- **A row.** An `id` the Agent or person chooses (letters, digits and `-`, at most 64, also what a tracking link carries), a title, a summary, a `type` and `channel` in the person's words (kept in lower case), a `state` (`draft`, `ready`, `published`, `dropped`), the full text, up to 8 tags, the `url` where it was published and the `trackingUrl` people follow (both https), `publishedAt`, `views` with `viewsAt`, up to 8 `media` (https links or file names), the Agent that last changed it (host-stamped) and a revision each change raises by one. Control characters (line breaks outside the text and summary) and anything that looks like a password, token or key are refused, never stored. A World keeps at most 5,000 rows.
- **Keeping.** The World tool `world_links`, as the gateway targets `links/save` and `links/read`, on the standing `worldlet` MCP server of the Electron and Node hosts alike. `save` creates or changes up to 50 rows by `id`, naming only the fields that change (a new row needs a title); `null` clears an optional field; publishing without `publishedAt` stamps it now. A row that changes nothing is left as it is. One bad row refuses the whole call, and nothing changes.
- **Reading.** `read` returns rows newest first (by when published, else made): particular `ids`, or narrowed by `state`, `channel` and `since` (`limit` up to 100). The answer is marked as untrusted content.
- **Grants.** None by default, and a Fox turn's `*/*` Grant never covers them (`OWN_GRANT_TARGETS`). Settings › Agent › Access gives two standing Grants (`linkGrant`), each change audited (`grant-read`, `ungrant-save`, …):
  - "Can see your tracked links" (`<agentId>-links-read`): `links/read`.
  - "Can keep your tracked links" (`<agentId>-links-save`): `links/save`. Keeping does not include seeing.
  Both are `read` Grants: a row only changes the person's own table, which they can see and change back, and is not a guarded write. Fox's own turns get an error for `world_links`.
- **Storage.** `state.tracked-links` in `world.sqlite`, all of one call's rows in one transaction ([storage](../items/STORAGE.md)), in the person's own World with private context allowed.
- **Audit.** Every call's decision is one `agent.audit` entry for the calling Agent. `node scripts/tracked-links-host-check.ts` checks all of this on a real `world.sqlite` through the standing server; `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkboxes.

## Agent artifacts

An Agent can save an artifact to the person's Journal on its own, outside any Fox turn: the result of a Scheduled routine, say, such as an hourly summary. The person sees it in the Journal like any other artifact, and other Agents can read it again ("the newest artifact Codex saved titled Hourly summary"). This is not the same as [Agent reports](#agent-reports): a report (`agents/report`) is an Agent's live status (working, idle, blocked), kept one per Agent and shown under its name in Settings; a Journal artifact is a card of content the Agent saved, kept with Fox's own cards in the Journal. The shapes are in [`contracts/agent-artifacts.ts`](../../contracts/agent-artifacts.ts); Core decides ([`agent-artifacts.ts`](agent-artifacts.ts)); the host keeps them (`agent-runtime/agent-artifacts.ts`). An Agent reaches them through the World tool `agent_artifacts`, as the gateway targets `agent-artifacts/save` and `agent-artifacts/read`, on the standing `worldlet` MCP server of the Electron and Node hosts alike.

- **Grants.** No Agent may save or read Journal artifacts by default, and a Fox turn's Grant never covers them: only the calling Agent's own Grants decide (`OWN_GRANT_TARGETS`). Fox's own turns get an error for `agent_artifacts`; Fox shows its own with `show_artifact`. Settings › Agent › Access gives two standing Grants (`artifactGrant`), each change audited (`grant-save`, `ungrant-read`, …):
  - "Can save to your Journal" (`<agentId>-artifacts-save`): `agent-artifacts/save`, and `agent-artifacts/read` of what it saved itself.
  - "Can read Agents' Journal artifacts" (`<agentId>-artifacts-read`): `agent-artifacts/read` of what every Agent saved. It does not include saving.
  Both are `read` Grants: a Journal artifact only shows something to the person in their Journal, which they can forget, and is not a guarded write.
- **Saving.** `agent-artifacts/save` takes a title (up to 80 characters on one line), a Markdown body (up to 12,000), an optional one-sentence brief (up to 160) and an optional `key`, a short stable name such as `hourly-2026-10-17T07`. Control characters and anything that looks like a password, token or key are refused, as for asks, and so is any other argument, an `agentId` included. The host makes an ordinary `answer` artifact from the conversation whose place is the Agent's name, stamped with the Agent from its token (`mergeArtifact`). With a key its ID is derived from the Agent and the key (`art-` and twelve hex digits of a SHA-256), so saving again with the same key replaces that artifact, which keeps its first time; a derived ID that holds something not this Agent's is refused. Without a key each save is a new artifact. Each Agent keeps its newest 48: a save forgets that Agent's oldest past that, and never Fox's or another Agent's artifacts beyond the World's own limit of 500.
- **Reading.** `agent-artifacts/read` returns only artifacts an Agent saved (with a host-stamped `agentId`), never Fox's own answers or Attention cards, which hold the person's private summaries. Newest first, optionally of one Agent (`agent`, its ID), with every word of `query` in the title, up to `limit` (10 by default, at most 50); each with its `id`, `agentId`, `title`, `brief`, `body` and `savedAt`, marked as untrusted content. Without "Can read Agents' Journal artifacts" an Agent reads only what it saved itself, and naming another Agent is refused.
- **Storage and the person.** They are rows of the `artifacts` table in `world.sqlite` ([storage](../items/STORAGE.md)), in the person's own World with private context allowed. The Journal lists them with every other artifact, and each save sends the page `worldlet:artifacts`. The person forgets one with × like any card. There is no new host action for the person, so nothing is added to `ROOM_ALLOWED`.
- **Audit.** Every call's decision is one `agent.audit` entry for the calling Agent, as for any World tool. `node scripts/agent-artifacts-host-check.ts` checks all of this on a real `world.sqlite` through the standing server; `agent-grants-check` checks the Grants and `your-agent-ui-check` the checkboxes.
